> 适用位置：飞书作品集页面中，放在项目介绍和产品截图之后。
> 当前口径：1000 样本评估来自 production-like 本地真实岗位池副本；正式域名线上 D1 账号已补充为真实入口 smoke 和产品截图证据。

## 1. 一句话结论

我没有只展示一个可点击 Demo，而是基于 5000+ 真实岗位池副本做了 1000 个求职组合评估，用来验证 ApplyFlow 的 Agent 输出是否可量化、可归因、可继续迭代。

评估结果显示：岗位方向判断和高优先级候选池有基础，但城市约束是最大 bad case。后续我做了第一轮地点约束修复，并用 L2 地点专项复测验证：历史城市不匹配的高优先级误推候选，修复后不再被直接推进，而是降级或提示用户确认地点。

这证明的是“误推治理有效”，不是“Top10 城市命中率已经提升”。Top10 城市命中率是否改善，还需要后续 L3 1000 样本全量回归确认。

## 2. 项目边界

ApplyFlow 当前不是全自动海投 Agent，也不是简历改写工具，而是求职决策与执行闭环 Agent / Agent workflow 原型。

当前已落地和可讲能力：

- 岗位判断与排序。
- 投递清单。
- Edge 插件辅助网申预填。
- 状态回填。
- 用户反馈与 bad case 记录。
- Evidence Log 小样本复测与 production-like 覆盖评估。

当前不包装成已落地能力：

- 简历改写。
- 求职信生成。
- 全自动投递。
- 自动提交。
- RAG。
- 多 Agent。
- 模型训练。

## 4. 为什么做评估

面试官如果只看 Demo，很难判断一个 AI Agent 项目是不是“对话玩具”。所以我把 Agent 输出拆成四类来评估：

| 输出类型 | 评估问题 |
|---|---|
| 决策输出 | Top1 / Top10 是否命中岗位方向、城市、行业 |
| 优先级输出 | Top1 是否属于高优先级候选，Top10 中高优先级候选质量如何 |
| 稳定性输出 | 是否能稳定返回 Top10，是否有接口错误或账号接错池 |
| Bad Case 输出 | 没命中时集中在哪类原因，下一步该怎么修 |

这轮评估不看“LLM 文案是否好看”，而是看 ApplyFlow 是否真的能帮助用户做岗位决策。

## 7. 结果解读

这轮结果不能简单理解为“系统好”或“系统坏”。更准确的结论是：

- 岗位方向判断有基础：Top1 岗位方向命中 88.8%，Top10 岗位方向命中 92.4%。
- 高优先级候选池不是乱给：Top1 属于高优先级候选的比例 90.0%，Top10 平均有 8.25 个高优先级候选。
- 城市约束是最大问题：Top10 城市命中只有 4.6%，高优先级候选城市命中只有 1.8%。

这说明 ApplyFlow 能较好判断“岗位方向是否相关”，但没有充分处理“地点是否满足用户偏好”。所以这不是一个单纯的模型能力问题，而是 Agent 输出规则和产品闭环问题。

## 8. Bad Case 归因

我没有看到城市命中低就直接调参数，而是拆成四层归因：

| 层级 | 问题 | 影响 |
|---|---|---|
| 数据层 | 真实岗位池 location 字段存在缺失、英文城市、多城市、全国、地点未说明 | Agent 看到的地点事实不稳定 |
| 约束层 | 用户城市偏好没有区分 hard constraint 和 soft preference | “只看上海”和“优先上海”被混在一起 |
| 优先级层 | 岗位方向很强时，城市不匹配仍可能被标成高优先级 | 高优先级候选池会误导用户 |
| 交互层 | 地点不确定时没有显式触发确认动作 | 用户看不到推荐的不确定性 |

一句话归因：

> 城市没命中不是简单的“规则错了”，而是地点约束没有贯穿数据标准化、用户偏好强弱、优先级判断和用户确认动作。

## 9. 第一轮修复：地点约束进入输出规则

改动目标：

- 不把地点缺失当成 0 分，避免误杀。
- 不让城市不匹配或地点缺失的岗位继续保持高优先级。
- 把地点不确定显式暴露给用户确认，而不是假装完全匹配。

第一轮行为验证：

| 测试场景 | 系统应该怎么判断 | 展示给用户的动作 |
|---|---|---|
| 岗位地点是上海，用户目标也是上海 | 地点符合偏好 | 可优先推进 |
| 岗位地点是北京，用户目标是上海 | 地点不符合偏好 | 先确认地点，不作为高优先级直接推进 |
| 岗位地点未说明 | 地点信息缺失 | 先确认岗位地点，不直接误杀 |
| 岗位地点是全国/多地 | 地点范围过宽 | 确认是否覆盖目标城市 |

验证命令：

```text
node scripts/validation/validate-job-scoring-derived-view.js
```

验证结果：通过，真实退出码为 0。

## 10. L2 地点专项复测

复测目的：

> L2 不重新证明全量 Top10 城市命中率，而是验证历史城市 bad case 是否还会被高优先级误推。

复测范围：

- 从历史 1000 样本结果中抽取 80 个城市 bad case。
- 共复测 700 个“修复前城市不匹配但仍高优先级”的候选岗位。
- 额外抽取 20 个地点命中的对照 case，共 103 个对照候选，验证修复没有把正确地点岗位误伤。

L2 复测结果：

| 对比项 | 修复前 | 修复后 |
|---|---:|---:|
| 历史城市不匹配岗位被高优先级直接推进 | 100.0% | 0.0% |
| 历史城市不匹配岗位被降级处理 | 0.0% | 100.0% |
| 历史城市不匹配岗位提示确认地点 | 0.0% | 100.0% |
| 地点命中的对照岗位仍可推进 | - | 100.0% |

复测命令：

```text
npm.cmd run eval:location-contract-l2
```

复测产物：

```text

tmp/location-contract-l2-eval/location-contract-l2-report.json
```

L2 结论：

> 这次修复不是简单把地点权重调大，而是把地点从普通打分项升级为 Agent 输出规则：地点不确定时要解释、确认，并进入后续复测。现在可以说“城市不匹配高优先级误推已在 L2 复测中降到 0”，但还不能说“Top10 城市命中率已经提升”。

## 12. 面试官可能追问

### Q1：你怎么评估 Agent 输出？

> 我不会只看模型最后生成了一段什么话。ApplyFlow 里 Agent 输出是结构化的，包括 Top10 排序、高优先级候选、推荐解释、下一步建议和 bad case 原因。所以我评估四类输出：决策输出是否命中岗位方向/城市/行业，高优先级候选是否真的值得推进，稳定性是否每次都能返回 Top10，失败输出是否能归因并进入下一轮迭代。

### Q2：城市命中这么低，为什么还能放作品集？

> 可以放，但不能包装成完美结果。城市命中低恰好证明我不是只展示好看的 Demo，而是能用评估发现系统短板。岗位方向和高优先级候选池表现说明系统有基础，城市 bad case 则说明下一轮要治理地点字段、城市偏好强弱、优先级降级和地点确认动作。后续 L2 复测里，700 个历史城市不匹配高优先级候选已经全部被降级或提示确认地点，说明这不是停留在分析，而是有修复和复测闭环。

### Q3：这是不是只是调排序规则？

> 如果只是把地点权重调大，那确实只是调规则。但我这轮做的是 Agent 输出规则治理。地点不匹配不是简单扣分，而是会影响是否给高优先级、是否建议推进、是否提示用户先确认地点。也就是说，Agent 不只是给一个分数，而是知道自己哪里不确定，并把不确定性交给用户确认。

### Q4：L2 能不能说明城市命中率已经提升？

> 不能。我会区分两个概念：L2 证明的是“城市不匹配的岗位不会再被高优先级误推”，也就是输出治理有效；但 Top10 城市命中率是否提升，要重新跑完整排序池才能证明。所以我会把它写成“误推率从 100% 降到 0%”，不会写成“Top10 城市命中率已提升”。

## 13. 90 秒口播

> 我这轮做了一个 production-like 的 Agent 输出评估，不是只展示 Demo。数据用的是 5000+ 真实岗位池副本，我构造了 20 个岗位方向、5 个城市、10 个行业，一共 1000 个组合，每个组合拉 Top10。
>
> 我评估的不是 LLM 文案，而是 Agent 的结构化决策输出：Top1 和 Top10 是否命中岗位方向、城市、行业；同时我额外看高优先级候选池，因为用户真正关心的是前排岗位靠不靠谱。
>
> 结果是 1000 个组合全部跑完，0 个错误，没有 Top10 不足。岗位方向表现不错，Top1 命中 88.8%，Top10 命中 92.4%；Top1 属于高优先级候选的比例是 90%，Top10 平均有 8.25 个高优先级候选，说明系统不是随便凑列表。
>
> 但最大 bad case 是城市：Top10 城市命中只有 4.6%，高优先级候选的城市命中也只有 1.8%。所以我的结论不是“模型完全不行”，而是地点约束没有足够进入数据标准化、用户偏好强弱、优先级判断和用户确认动作。
>
> 后续我做了第一轮地点约束修复和 L2 复测：从历史 1000 样本里抽了 80 个城市 bad case，复测 700 个修复前高优先级误推的候选，修复后直接推进率从 100% 降到 0%，全部转为降级或确认地点。同时 103 个地点命中的对照候选仍 100% 可推进，说明没有把正确岗位误伤。这个结果证明误推治理有效，但还不能证明 Top10 城市命中率已经提升，后面还需要 L3 全量回归。
