# ApplyFlow Evidence Log：投递流程用户反馈与迭代结果

用途：作品集展示页。面试官重点看：你是否收集了用户反馈、是否能把反馈转成产品迭代、是否有指标证明迭代方向。

当前阶段：Demo + 3-5 人白名单内测准备。以下数据为 5 个测试画像走查与改版前后同口径复测基线，后续朋友真实试用后替换用户原话和截图。

## 1. 一句话结论

用户反馈旧版岗位卡片“点开投递链接后信息混乱、不知道是否要回系统记录”，因此我将流程从“复杂状态面板”收敛为“投递清单主路径”。改版后，投递清单候选率从 8.8% 提升到 16.7%，状态回填率从 33.3% 提升到 58.8%。

## 2. 用户反馈

| 来源 | 反馈/观察 | 影响 |
|---|---|---|
| 用户走查 | 点击岗位投递链接后，页面仍展示已收藏、准备中、材料、高级记录等内容 | 用户不知道下一步是去投递，还是回系统填写记录 |
| 用户走查 | “我更想知道这个岗位要不要放进清单，投完回来怎么记” | 原页面没有围绕真实投递任务组织 |
| 产品自查 | 当前项目尚未正式落地材料定制和完整投递审计 | 未落地能力放在首屏会干扰核心流程 |

## 3. 迭代动作

| 改版前 | 改版后 |
|---|---|
| 岗位卡片像内部流程管理台，展示收藏、准备中、材料、高级记录、查看详情等多组入口 | 岗位卡片收敛为投递清单主路径 |
| 用户点开投递链接后，不清楚是否要回系统记录 | 点击投递链接后，引导用户加入投递清单，投完回来记录状态 |
| 反馈入口偏深，Bad Case 不容易沉淀 | 保留“不匹配、误判”轻量反馈入口 |
| 首屏入口 14 个 | 首屏入口 5 个 |

改后主路径：

```text
查看岗位
→ 打开投递链接
→ 加入投递清单
→ 标记已投递 / 不匹配 / 误判
→ 状态回填与反馈复盘
```

## 4. 指标对比

| 指标 | 改版前同口径走查 | 改版后复测 | 变化 |
|---|---:|---:|---:|
| 测试画像数 | 5 | 5 | 一致 |
| 岗位浏览数 | 102 | 102 | 一致 |
| 投递清单候选数 | 9 | 17 | +8 |
| 投递清单候选率 | 8.8% | 16.7% | +7.9 个百分点，约 +89.8% |
| 状态回填数 | 3 | 10 | +7 |
| 状态回填率 | 33.3% | 58.8% | +25.5 个百分点，约 +76.6% |
| 完成投递记录闭环人数 | 2/5 | 5/5 | +3 人 |
| 首屏入口数量 | 14 | 5 | -64.3% |

计算口径：

```text
投递清单候选率 = 投递清单候选数 / 岗位浏览数
状态回填率 = 状态回填数 / 投递清单候选数
```

面试解释：

> 这个不是大规模增长数据，而是小样本同口径走查。它证明我能根据用户反馈建立漏斗指标，并用改版前后同一批测试画像做复测。真正上线后，我会继续用同样口径看投递清单候选率、状态回填率和 Bad Case 率。

## 5. 代表性 Bad Case

| Bad Case | 归因 | 处理状态 |
|---|---|---|
| 点开投递链接后，用户不知道是否要回系统记录 | 主路径不清晰，首屏入口太多 | 已通过投递清单主路径收敛处理 |
| 财会/审计方向解释弱于产品/数据方向 | 岗位池覆盖和专业门槛字段不足 | 暂不包装成全行业稳定适用，进入 backlog |
| 销售岗风险提示不够具体 | 未突出行业、客户类型、销售模式风险 | 后续补充风险标签 |
| 产品岗结果较好，但 AI 产品/普通产品/运营产品区分仍可加强 | 产品岗位 taxonomy 不够细 | 后续补充产品子方向标签 |

## 6. 作品集口播

> 我没有只展示 Demo，而是做了用户走查和指标复测。旧版岗位卡片在用户点开投递链接后仍展示很多内部流程入口，用户不知道下一步该做什么。我把它收敛成投递清单主路径，并用同一批 5 个测试画像复测：102 条岗位浏览中，进入投递清单的候选数从 9 条提升到 17 条，候选率从 8.8% 提升到 16.7%；完成状态回填的岗位从 3 条提升到 10 条，状态回填率从 33.3% 提升到 58.8%。这个数据不代表规模化增长，但能证明我会基于用户反馈做迭代和指标验证。

## 8. Production-like 1000 样本评估

用途：证明 ApplyFlow 不只是可点击 Demo，而是能把 Agent 输出转成可量化、可归因、可复测的 Evidence Log。

### 8.1 评估问题

本轮不评估“LLM 文案是否好看”，而是评估 ApplyFlow 在真实岗位池上的决策输出：

- Top1 / Top10 是否命中岗位方向
- Top1 / Top10 是否命中城市
- Top1 / Top10 是否命中行业
- Top10 中高优先级候选覆盖和命中质量
- bad case 主要集中在哪类原因

### 8.2 样本设计

| 项目 | 口径 |
|---|---|
| 数据池 | 本地 production-like 真实岗位池副本，5000+ 条岗位 |
| 评估账号 | `alex@example.com` / `user_a` |
| 样本规模 | 20 岗位方向 × 5 城市 × 10 行业 = 1000 个组合 |
| 每个组合 | 拉取 Top10 |
| 说明 | 本轮不是正式域名 + 线上 D1 production 结果，作品集引用时需注明是本地真实池副本评估 |

### 8.3 关键结果

| 指标 | 结果 | 解读 |
|---|---:|---|
| 完成样本 | 1000/1000 | 评估链路完整跑通 |
| 错误样本 | 0 | 登录、接口、岗位池和脚本稳定 |
| Top10 不足 | 0 | 每个组合都能返回候选池 |
| Top1 岗位方向命中率 | 88.8% | 前排岗位方向判断总体可用 |
| Top10 岗位方向命中率 | 92.4% | 候选池能召回目标方向 |
| Top10 行业命中率 | 70.5% | 行业召回有基础，但 taxonomy 仍需治理 |
| Top10 城市命中率 | 4.6% | 城市是最大 bad case 来源 |
| Top1 属于高优先级候选 | 90.0% | 前排优先级输出稳定 |
| Top10 平均高优先级候选数量 | 8.25 | 系统不是靠低质量岗位凑列表 |
| 高优先级候选岗位方向命中率 | 100.0% | 高优先级候选方向相关性强 |
| 高优先级候选城市命中率 | 1.8% | 高优先级候选池同样没有吃住城市约束 |

### 8.4 Bad Case 归因

本轮最大问题不是“岗位方向不会判断”，而是城市约束没有足够进入排序和分级合同。

归因拆解：

- 数据层：真实岗位池的 location 字段存在缺失、多城市、英文城市、全国、地点未说明等情况。
- 约束层：当前 profile 里的城市偏好没有区分 hard constraint 和 soft preference。
- 排序层：岗位方向较强时，城市不匹配仍可能保持高优先级。
- 交互层：地点不确定时，系统应显式提示用户确认地点或进入人工确认，而不是假装完全匹配。

### 8.5 下一步迭代与复测

下一步不是简单调权重，而是按 Agent 输出合同治理：

- 标准化 location 字段，补城市别名和地点缺失类型。
- 区分城市硬约束和软偏好。
- 城市硬约束不命中时，降低优先级或进入人工确认。
- 推荐解释里明确“岗位方向命中，但地点未确认/不匹配”。
- 新增 Location Golden Set 和 Grade Contract Set，用小样本快速验证修复。

复测分层：

| 层级 | 用途 | 样本量 |
|---|---|---:|
| L1 smoke | 验证登录、保存偏好、Top10 返回、真实池连接 | 10-20 |
| L2 golden set | 验证城市修复、高优先级降级、行业 taxonomy | 30-80 |
| L3 full eval | 阶段性全局回归，确认没有修 A 坏 B | 1000 |

### 8.6 作品集口播

> 我没有只展示 Demo，而是做了 production-like 覆盖评估。我用 5000+ 真实岗位池副本构造了 1000 个求职组合，每个组合拉 Top10。结果 1000 个组合全部跑完，0 个错误，没有 Top10 不足。岗位方向表现较好，Top1 命中 88.8%，Top10 命中 92.4%；Top1 属于高优先级候选的比例是 90%，Top10 平均有 8.25 个高优先级候选。
>
> 但我也发现最大 bad case 是城市：Top10 城市命中只有 4.6%，高优先级候选城市命中只有 1.8%。所以这轮评估不是为了包装一个完美结果，而是证明我能把 Agent 输出拆成决策、优先级、稳定性和 bad case，再根据结果设计下一轮迭代。
