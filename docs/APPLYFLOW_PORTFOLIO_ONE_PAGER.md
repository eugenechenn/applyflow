# AI 求职 Agent 作品集：ApplyFlow

最后更新：2026-06-02

## 1. 摘要

ApplyFlow 是一个面向求职场景的 AI 求职执行 Agent，核心不是“一键海投”或“简历改写”，而是围绕“先筛后投”重构求职流程：帮助用户批量处理岗位、建立求职偏好、做可解释排序、沉淀投递清单、通过 Edge 插件辅助真实官网网申字段预填、记录投递状态，并通过用户反馈和 Bad Case 持续优化。

一句话定位：

> ApplyFlow 用 AI 帮用户先判断哪些岗位值得投入时间，再用投递清单、Edge 插件辅助网申和状态回填把求职从“手工海投”变成可解释、可辅助执行、可追踪、可复盘的执行流程。

## 2. 用户问题

目标用户：

- 同时浏览几十到上百个岗位的求职者。
- AI / 产品 / 数据 / 运营等方向，需要持续判断岗位优先级的人。
- 希望减少无效海投，并记录自己投递进展的人。

核心痛点：

- 岗位信息太多，逐条手工判断成本高。
- 传统招聘平台只展示岗位，不解释“为什么这个岗位值得投”。
- 通用 AI 工具容易停留在单点生成，缺少投递状态管理和反馈复盘。
- 用户点开投递链接后，容易失去记录，不知道哪些岗位看过、哪些值得投、哪些已经投完。
- 进入企业官网网申后，需要重复填写基础资料，容易增加投递成本和中断率。

## 3. 核心流程

```text
岗位导入
→ 标准化 / 去重
→ 用户偏好建模
→ 五维可解释排序
→ 投递清单
→ 多岗位对比
→ 打开投递链接
→ Edge 插件辅助预填可识别字段
→ 用户确认提交
→ 状态回填
→ 用户反馈 / Bad Case
→ 迭代复盘
```

当前最核心的用户路径：

```text
查看岗位
→ 打开投递链接
→ 加入投递清单
→ 需要时启用网申辅助插件
→ 企业官网预填可识别字段
→ 用户检查并提交
→ 标记已投递 / 不匹配 / 误判
→ 状态回填与反馈复盘
```

## 4. 产品亮点

- 求职执行闭环：不是只生成一段建议，而是把岗位筛选、投递清单、多岗位对比、状态回填和用户反馈串成完整流程。
- 可解释岗位优先级：将岗位匹配拆解为目标角色、行业方向、城市偏好、公司类型、投递可行性等维度，不只给分数，还给推荐理由、风险点和下一步动作。
- 投递主路径优化：根据用户反馈，将岗位卡片从“复杂流程状态面板”收敛为“投递清单主路径”，减少用户投递后的记录成本。
- 一键辅助网申：个人资料页沉淀网申辅助资料，Edge 插件在真实企业官网手动触发预填可识别字段，减少重复填写。
- 反馈驱动迭代：用户可以反馈不匹配、误判和 Bad Case，帮助后续优化岗位分类、推荐解释和风险提示。
- 评测与回归验证：基于 5000+ 条真实岗位数据检查不同求职画像下的排序稳定性，并用固定脚本验证排序合同、用户归属和关键写路径。

## 5. 架构与 AI 边界

ApplyFlow 的重点不是让模型自由做决定，而是把 AI 放进可控流程。

模型负责：

- 理解岗位描述和用户偏好。
- 生成匹配理由、风险点和候选建议。
- 辅助解释为什么某个岗位更值得优先投。

系统负责：

- 状态流转：岗位浏览、投递清单、状态回填、反馈记录。
- 权限校验：写入以认证用户为准，不信任前端透传 userId。
- 执行门禁：外部投递不默认全自动提交，保留用户确认。
- 评测回归：排序、真实池、演示池、用户隔离、伪造 userId 拒绝等脚本验证。

插件负责：

- 读取用户在个人资料页维护的网申辅助资料。
- 在企业官网网申页由用户手动触发，预填可识别字段。
- 不自动提交、不绕过验证码、不保证覆盖附件上传或复杂多步骤表单。
- 对格式差异大的时间类字段保留用户手动确认。

用户负责：

- 最终决定是否投递。
- 检查插件预填内容并确认高风险动作。
- 反馈不匹配、误判和真实投递结果。

面试表达：

> 我的设计不是“让 AI 替用户做完所有事”，而是让 AI 做语义判断和解释建议，让插件减少重复填写，让系统负责状态、权限、门禁和审计，让用户保留最终投递和提交决策。

## 6. 内测证据与指标

当前阶段：线上体验版 + 3-5 人白名单内测准备；已完成一轮本地真实池副本的 production-like 1000 样本评估。

数据口径：

- 以下为 5 个测试画像的改版前后同口径走查。
- 不是大规模上线增长数据。
- 后续朋友真实试用后，会替换用户原话、截图和复测记录。

投递流程迭代指标：

| 指标 | 改版前 | 改版后 | 变化 |
|---|---:|---:|---:|
| 测试画像数 | 5 | 5 | 一致 |
| 岗位浏览数 | 102 | 102 | 一致 |
| 投递清单候选数 | 9 | 17 | +8 |
| 投递清单候选率 | 8.8% | 16.7% | +7.9 个百分点，约 +89.8% |
| 状态回填数 | 3 | 10 | +7 |
| 状态回填率 | 33.3% | 58.8% | +25.5 个百分点，约 +76.6% |
| 完成投递记录闭环人数 | 2/5 | 5/5 | +3 人 |
| 首屏入口数量 | 14 | 5 | -64.3% |

计算口径：

```text
投递清单候选率 = 投递清单候选数 / 岗位浏览数
状态回填率 = 状态回填数 / 投递清单候选数
```

面试解释：

> 这个指标不是为了证明规模化增长，而是证明我能把用户反馈转成可复测的产品漏斗。用户反馈旧版投递链路混乱后，我把主路径收敛为投递清单，并用同一批测试画像复测，投递清单候选率从 8.8% 提升到 16.7%。

Production-like 1000 样本评估：

| 指标 | 结果 | 解读 |
|---|---:|---|
| 完成样本 | 1000/1000 | 评估链路完整跑通 |
| 错误样本 | 0 | 登录、接口、岗位池和脚本稳定 |
| Top10 不足 | 0 | 每个组合都能返回候选池 |
| Top1 岗位方向命中率 | 88.8% | 前排岗位方向判断总体可用 |
| Top10 岗位方向命中率 | 92.4% | 候选池能召回目标方向 |
| Top10 行业命中率 | 70.5% | 行业召回有基础，但 taxonomy 仍需治理 |
| Top10 城市命中率 | 4.6% | 城市是最大 bad case 来源 |
| Top1 属于高优先级候选 | 90.0% | 前排优先级输出稳定 |
| Top10 平均高优先级候选数量 | 8.25 | 系统不是靠低质量岗位凑列表 |
| 高优先级候选岗位方向命中率 | 100.0% | 高优先级候选方向相关性强 |
| 高优先级候选城市命中率 | 1.8% | 高优先级候选池同样没有吃住城市约束 |

解释口径：

> 这轮评估不是为了包装一个完美结果，而是为了把 Agent 输出变成可量化证据。结果说明岗位方向和高优先级候选池有基础，但城市约束明显不足。下一步不是简单调参数，而是治理地点数据标准化、城市硬/软偏好、高优先级降级和地点确认动作。

L2 地点专项复测：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 城市不匹配岗位被高优先级直接推进 | 100.0% | 0.0% |
| 城市不匹配岗位被降级处理 | 0.0% | 100.0% |
| 城市不匹配岗位提示确认地点 | 0.0% | 100.0% |
| 地点命中对照岗位仍可推进 | - | 100.0% |

> 复测范围：从历史 1000 样本中抽取 80 个城市 bad case，复测 700 个修复前高优先级误推候选；另取 103 个地点命中对照候选确认没有误伤。这个结果证明“误推治理有效”，但还不能直接宣称 Top10 城市命中率已提升，后续仍需 L3 全量回归。

## 7. 代表性迭代

### 迭代：投递链接后的动作收敛

用户反馈：

> 点开投递链接后，页面还展示已收藏、准备中、材料、高级记录等内容，不知道下一步是去投递，还是回系统填写记录。

问题归因：

- 旧页面更像内部流程管理台。
- 当前项目尚未正式落地材料定制和完整投递审计。
- 未落地能力放在首屏，会干扰真实求职动作。

迭代动作：

- 隐藏材料和高级记录在首屏的干扰。
- 保留打开投递链接、加入投递清单、标记已投递、不匹配、误判。
- 将主路径定义为“查看岗位→打开投递链接→加入投递清单→状态回填”。

迭代结果：

- 投递清单候选率：8.8% → 16.7%。
- 状态回填率：33.3% → 58.8%。
- 完成投递记录闭环人数：2/5 → 5/5。
- 首屏入口数量：14 → 5。

### 当前辅助网申边界

已覆盖能力：

- 个人资料页维护网申辅助资料。
- 打开官网投递链接前提示是否启用插件辅助填写。
- Edge 插件在企业官网手动触发预填可识别字段。

明确不包装为：

- 不是全自动海投。
- 不是自动提交。
- 不绕过验证码、附件上传或复杂多步骤表单。
- 不承诺替用户完成材料适配。

## 8. 当前不足与下一步

当前不足：

- 用户规模仍小：当前是 demo + 3-5 人白名单内测准备，不是公开 SaaS，也不是规模化增长阶段。
- 指标仍是小样本走查：投递清单候选率和状态回填率来自 5 个测试画像的改版前后同口径复测，还需要真实朋友试用补强证据。
- 岗位方向覆盖不均：产品、数据、运营方向表现更适合作品集展示；财会/审计、销售等方向的岗位池和解释粒度仍需补充。
- 城市约束明显不足：production-like 1000 样本里 Top10 城市命中率只有 4.6%，高优先级候选城市命中率只有 1.8%；L2 已验证误推治理有效，但还需要 L3 全量回归确认 Top10 城市命中率是否提升。
- 线上观测还不完整：目前有离线回归、走查指标和 production-like 样本评估，但还缺完整埋点、P95 延迟、错误率、用户漏斗看板和长期投递结果追踪。
- Auth 与生产化仍需补齐：当前不是 Production Auth Ready，扩大内测前需要接入托管 Auth，并继续验证用户数据隔离。
- 材料定制功能当前未落地：作品集和简历中不写简历改写或自动材料生成能力。
- 辅助网申仍是基础预填阶段：当前重点是可识别字段预填，不是全站自动投递；复杂字段、附件、验证码和最终提交仍由用户处理。
- 代码仍有工程债：前端和 orchestration 层仍有大文件，需要继续拆分模块，降低长期维护成本。

下一步：

- 用 3-5 位朋友真实试用替换当前走查草稿，补充真实用户原话、截图、耗时和 Bad Case。
- 固化投递漏斗埋点：岗位浏览数、投递清单候选数、状态回填数、误判反馈数、Bad Case 率。
- 建立分层评估：L1 快速冒烟保主链路，L2 地点专项复测 / 高优先级候选专项复测快速验证城市修复，L3 1000 样本阶段性回归。
- 针对城市 bad case，补地点字段标准化、城市硬/软偏好、高优先级降级策略和地点确认动作。
- 固化辅助网申埋点和验证：插件触发次数、字段预填成功率、用户手动修正字段、放弃填写原因。
- 针对产品、数据、运营方向优先补充岗位 taxonomy，提高推荐解释粒度。
- 将真实用户反馈沉淀为 Bad Case 台账，按“数据问题 / 排序问题 / 解释问题 / 流程问题 / 权限问题”归因。
- 接入托管 Auth，继续完善白名单用户隔离、写路径归属校验和用户数据安全边界。
- 增加线上观测：P95 latency、API error rate、fallback rate、用户漏斗和单次 AI 调用成本。
- 拆分前端大文件和 workflow controller，把已验证的投递主路径沉淀成更清晰的模块。

面试收尾：

> 我不会把 ApplyFlow 包装成已经成熟的商业 SaaS。当前最有价值的是，它已经从可用线上体验进入到“用户反馈驱动迭代”和“Agent 输出评估”的阶段：我能明确记录用户问题、归因原因、做产品改动，用投递漏斗指标复测效果，也能用 1000 样本覆盖评估发现城市约束这类系统短板。下一步才是扩大真实用户、补齐正式域名、Auth、埋点和线上观测。
