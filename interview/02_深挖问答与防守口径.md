# 02 AI 岗位深挖问答与防守口径

最后更新：2026-06-02

## 1. 使用方法

这份文档不是逐字背诵稿，而是面试深挖时的“答题骨架”。每道题都按同一种逻辑回答：

```text
先讲概念
-> 讲主流项目怎么做
-> 如果 ApplyFlow 做过，讲具体证据
-> 如果没做过，讲诚实边界和接入验证
```

注意：不要每道题都硬扯 ApplyFlow。能联系项目就联系，不能联系就讲行业方法和防守边界。

## 2. 高频控场句

| 被问到 | 先说 |
|---|---|
| Agent 和工作流 | 我不会把所有自动化都包装成 Agent，确定流程交给工作流，不确定判断才交给模型。 |
| 工具调用越权 | Prompt 是软约束，真正可靠的是结构化参数、权限校验、状态机、日志和人工确认。 |
| Agent 评估 | 我不只看有没有返回结果，而是看决策、动作和状态是否符合用户目标。 |
| 结构化输出 | AI 输出要从“自然语言建议”变成“可校验、可降级、可复测的输出合同”。 |
| RAG / 记忆 / 多 Agent | 我不会硬说 ApplyFlow 做了，我先讲它解决什么问题，再讲如果接入怎么验证。 |
| Claude Code / Codex | Coding Agent 的壁垒不是模型会写代码，而是有没有 harness 把它管进可验证流程。 |
| 被质疑只是调规则 | 如果只改权重是调规则，但如果影响等级、动作、解释和复测，就是输出合同治理。 |

## 补充一：面试官喜欢的六边形答题法

AI 岗位面试官经常会把一个问题连续追问到细节崩溃。不要只答“我用了某技术”，要尽量同时覆盖六个维度：

| 维度 | 面试官在看什么 | ApplyFlow 怎么接 |
|---|---|---|
| 业务 | 你是否理解用户痛点和任务闭环 | 求职者不是缺一句文案，而是缺岗位筛选、投递清单和状态复盘 |
| 技术 | 你是否知道方案取舍，而不是只调 Prompt | 结构化输出、地点约束修复、状态机、权限校验 |
| 指标 | 你是否能把结果量化 | 候选率 8.8% -> 16.7%，回填率 33.3% -> 58.8%，1000 样本 Top10 方向命中 92.4% |
| 风险 | 你是否知道 AI 会错、会慢、会越权 | 插件不自动提交，城市不确定降级，非法写入 400/401/403 |
| 协作 | 你是否能和算法、研发、测试对齐 | 用样本集、bad case、输出合同和验收口径对齐 |
| 复盘 | 你是否能面对失败和冷启动 | 城市命中 4.6% 后先做 L2 误推治理复测，再阶段性全量回归 |

口播模板：

> 我会先讲业务目标，再讲技术方案，最后讲指标和复盘。AI 项目最怕只说“体验更好”，所以我会主动补上线后指标，比如采纳率、二次追问率、平均 token 消耗、延迟、留存、错误率和人工介入率。

## 3. Agent 和工作流有什么区别

概念回答：

> Chatbot 主要回答问题，工作流按固定步骤推进，Agent 更强调理解目标、选择工具、处理不确定性并推进任务。但真实业务里，Agent 不能自由乱跑，必须被工作流、权限和评估机制约束。

主流做法：

- 简单确定流程：用规则和工作流，不要硬上 Agent。
- 有不确定判断：让模型做分类、匹配、解释、规划。
- 有工具执行：给工具参数 schema、权限校验和失败兜底。
- 高风险动作：需要审批、人工确认或二次校验。

ApplyFlow 怎么讲：

> ApplyFlow 如果只看排序函数，确实不能硬叫 Agent。它的 Agent 性在 Decision / Control / Action / Feedback 闭环：AI 判断岗位是否匹配，系统把判断转成投递清单和状态，插件辅助官网预填，用户反馈再回到 Bad Case 和 Evidence Log。

防守句：

> 我更准确的说法是 ApplyFlow 是 Agent workflow 原型，不是完全自治的强 Agent。

## 4. 怎么评估 Agent 输出

概念回答：

> Agent 输出不只有文本，也包括决策、工具调用、状态变化和下一步动作。评估时不能只看“有没有回答”，要看它是否完成用户目标、过程是否可控、成本和风险是否可接受。

主流评估维度：

| 维度 | 看什么 |
|---|---|
| 结果 | 任务是否成功，Top1/Top10 是否命中，状态是否正确 |
| 过程 | 工具调用顺序、参数、解释、失败恢复、是否越权 |
| 系统 | 延迟、成本、稳定性、缓存、是否需要强模型 |
| 安全 | 权限、数据隔离、人工确认、异常回滚 |

ApplyFlow 标准回答：

> 我评估 Agent 输出时，不只看它有没有返回 Top10，而是看结构化输出是否符合用户目标。ApplyFlow 里 Agent 输出包括 Top10 排序、高优先级候选、推荐解释和下一步动作。
>
> 1000 样本评估里，岗位方向表现不错，Top1 方向命中 88.8%，Top10 方向命中 92.4%；高优先级候选岗位方向命中也很高。但城市命中很低，Top10 城市命中只有 4.6%，高优先级候选城市命中只有 1.8%。
>
> 我的判断不是模型完全不行，而是城市约束没有进入完整的 Agent 输出规则。系统知道岗位方向相关，但没有充分处理地点字段脏、城市硬/软偏好、高优先级降级和地点不确定提示。
>
> 下一步我会先做地点标准化，再区分城市硬约束和软偏好；如果硬约束不命中，就不能继续作为高优先级直接推进，而要降级或提示用户确认地点。L2 复测里，700 个历史误推候选修复后直接推进率从 100.0% 降到 0.0%；最后还要阶段性再跑 1000 样本防止全局回归。

一句总结：

> 这不是简单调规则，而是把 Agent 的输出从“给一个看似合理的岗位列表”，升级成“可解释、可降级、可确认、可复测”的决策系统。

## 5. 结构化输出和输出合同是什么

概念回答：

> 结构化输出是让模型按固定字段返回结果，比如等级、原因、下一步动作，而不是只给一段自然语言。输出合同更进一步，它规定这些字段如何影响系统动作、降级和复测。

主流做法：

- 用 JSON Schema 或类型定义约束字段。
- 字段值使用枚举，避免模型自由发挥。
- 服务端二次校验，不信模型直接写状态。
- 输出进入日志和评估集，方便追踪 bad case。
- 关键动作需要人确认或系统审批。

ApplyFlow 例子：

- Top10 排序：决定候选池。
- 高优先级候选：决定是否值得前排推进。
- 推荐解释：告诉用户为什么。
- 下一步建议：告诉用户下一步是投递、确认地点还是复核。
- 地点确认：地点匹配、地点不匹配、地点未知、全国/多地。

防守句：

> 如果只是让模型写“我推荐你投这个岗位”，那很虚；但如果它必须输出等级、原因、地点状态和下一步动作，并且这些字段会进入降级和复测，这才是可治理的 Agent 输出。

## 6. AI 生成错了、工具参数错了怎么办

概念回答：

> 不要把安全押在 Prompt 上。Prompt 可以提醒模型，但不能替代 schema、权限、状态机和人工确认。

主流做法：

- 输入层：外部网页、用户输入、历史记录都当作不可信。
- 输出层：结构化字段校验，非法值拒绝。
- 工具层：工具参数 schema、权限范围、最小权限原则。
- 状态层：用服务端真实身份和状态机做 source-of-truth。
- 风险层：高风险动作审批或人工确认。
- 日志层：记录工具调用、失败原因和回滚点。

ApplyFlow 例子：

- 前端传来的 `payload.userId` 不能作为用户身份依据。
- 非法 JSON / 参数走 400。
- 未登录走 401。
- 越权或伪造用户走 403。
- 插件只预填，不自动提交、不绕过验证码。

面试句：

> 模型可以建议“这个岗位值得投”，但不能直接把状态写成“已投递”。真实状态必须由用户动作和服务端校验确认。

## 7. 什么是 Guardrails、审批和人工确认

概念回答：

> Guardrails 可以理解为 AI 系统的护栏，用来检查输入、输出或工具调用是否安全、合规、符合任务边界。审批和人工确认是高风险动作的最后一道门。

主流做法：

- 输入护栏：过滤提示注入、敏感信息、越权请求。
- 输出护栏：检查结构、事实、合规和风险等级。
- 工具护栏：检查工具能不能被调用、参数是否越权。
- 人工确认：退款、提交、删除、投递、封禁等高风险动作需要人确认。
- 追踪记录：每次模型输出、工具调用、审批结果都要留痕。

ApplyFlow 映射：

- 投递提交：必须用户确认。
- 插件预填：只做低风险辅助。
- 状态写入：必须认证用户和合法状态。
- 城市不确定：触发确认地点，而不是继续作为高优先级推进。

一句洞见：

> AI 产品的关键不是让模型更大胆，而是让系统知道什么时候该停下来问人。

## 补充二：AI 产品最大局限是什么，怎么突破

面试官问法：

- 你觉得目前 AI 产品最大的局限是什么？
- 幻觉问题怎么解决？
- 你会怎么让用户信任 AI 输出？

不要这么答：

> 最大局限是伦理问题、隐私问题、模型不够强。

这些太虚，容易被追问到没细节。

更好的回答：

> 我认为当前 AI 产品最大的局限不是单纯“模型会幻觉”，而是用户很难感知系统什么时候不确定。幻觉可以靠 RAG、结构化输出、强约束 Prompt、工具校验和人工抽检缓解，但如果产品层面没有把不确定性暴露出来，用户会把所有答案都当成同等可信。

主流缓解方式：

| 问题 | 技术侧 | 产品侧 |
|---|---|---|
| 幻觉 | RAG、引用、结构化输出、工具校验 | 标注证据来源，不确定时提示用户确认 |
| 低置信度 | 多轮验证、模型自检、规则校验 | 置信度提示、二次确认、人工复核入口 |
| 意图误判 | 意图识别、上下文补全、澄清问题 | 让用户选择目标或纠正偏好 |
| 信息过期 | 联网搜索、实时数据源、缓存失效 | 显示更新时间，提示“需要重新确认” |
| 高风险动作 | 权限、审批、状态机 | 提交、删除、支付、投递等动作必须用户确认 |

ApplyFlow 映射：

> ApplyFlow 的城市 bad case 就是一个典型例子。系统知道岗位方向相关，但没有把地点不确定显式暴露给用户，所以高优先级候选池会误导用户。我的修复不是只调大地点权重，而是让城市不匹配、地点缺失、全国/多地范围进入地点确认流程，提示用户先确认地点。

30 秒口播：

> 我觉得 AI 产品最大局限是“不确定性没有被产品化”。模型不确定时，不能只靠后端调参或 Prompt，而要在产品层给用户信号：比如置信度、证据引用、二次确认、联网搜索或人工复核。ApplyFlow 里城市命中低就是这个问题，所以我把地点从普通分数项升级成输出合同，不确定时降级并触发确认地点。

## 8. Eval Harness 怎么搭

概念回答：

> Eval harness 是把模型或 Agent 的输出放进固定任务、固定数据、固定评分和回归门禁里。它的价值是让一次看似不错的 Demo 变成可复测的证据。

主流做法：

1. 定义任务：模型到底要完成什么。
2. 固定输入：用户画像、数据池、场景和约束。
3. 固定输出：字段、状态、工具调用或动作结果。
4. 定义评分：代码评分、人工抽检、模型辅助裁判组合。
5. 记录轨迹：输入、输出、工具、状态和失败原因。
6. 分层复测：小样本 smoke、专项 golden set、阶段性全量评估。

ApplyFlow 例子：

- L1 smoke：验证登录、Top10 返回、真实池连接。
- L2 地点专项复测：验证城市命中和地点确认。
- L2 高优先级候选专项复测：验证城市不匹配时是否降级或要求确认。
- L3 1000 样本：阶段性全局回归。

防守句：

> 我不会每改一次都跑 1000 条，那样效率很低。日常用 L1/L2 保链路和专项修复，阶段性再跑 L3 防止全局回归。

## 9. LLM-as-a-Judge 怎么看

概念回答：

> 模型当裁判适合辅助评估开放式解释，但不能单独做最终裁判，因为裁判本身也会幻觉、偏好漂移或漏看证据。

主流组合：

- 确定性问题：代码评分器、数据库状态比对、schema 校验。
- 语义解释：模型辅助评分或人工抽检。
- 高风险样本：人工复核。
- 回归门禁：固定评估集和指标阈值。

ApplyFlow 映射：

- Top10 是否返回：代码判断。
- 方向、城市、行业是否命中：脚本和规则辅助判断。
- 推荐解释是否合理：人工或模型抽检。
- 用户是否采纳：看投递清单和状态回填。

一句防守：

> 我不会让另一个模型一句话判定系统好坏，而是把代码评分、状态比对、人工抽检和 Evidence Log 组合起来。

## 10. RAG、上下文和 Memory 总览

这组题是 AI 岗位高频深挖点，不能只背定义。面试官真正想听的是：你知不知道模型“看见信息”的几种方式有什么区别，以及为什么顶级 Agent 不会简单地把所有东西塞进 RAG。

一句总控：

> RAG 解决“去哪找资料”，长上下文解决“这次能看多少”，Memory 解决“哪些历史值得留下来以后再用”。三者经常组合，但不能互相替代。

对比表：

| 概念 | 人话解释 | 适合场景 | 主要风险 |
|---|---|---|---|
| 长上下文 | 本轮直接把大量材料放进模型窗口 | 一次性读合同、简历、代码片段、长报告 | 成本高、噪声多、模型可能抓不住重点 |
| RAG | 先检索相关资料，再把少量证据放进上下文 | 企业知识库、政策、文档、面经、历史记录 | 召回错、引用错、旧资料污染答案 |
| Memory | 把长期有用的信息保存起来，未来按任务取用 | 用户偏好、项目规则、历史反馈、长期任务 | 记错、取错、过期、不该跨用户泄露 |
| Context Engineering | 决定本轮模型该看什么、按什么优先级看 | Agent、Coding Agent、长任务 | 上下文污染、token 浪费、遗漏关键事实 |

顶级项目延伸：

- Claude Code 公开文档更强调显式项目记忆、自动 memory、上下文压缩、按需读取和工具权限。它不是简单“所有历史做向量 RAG”，而是让 Agent 在当前任务里读取真实文件、遵守项目规则，并在 compact 后保留关键上下文。
- OpenAI Agents / Codex 这类系统也强调 progressive disclosure，也就是先给模型摘要、索引、规则和当前任务，再让它按需读取更细资料，而不是一开始把全仓库或全知识库都塞进去。
- Anthropic effective agents 的取舍也类似：先用简单、可组合、可验证的方法，只有当复杂 Agent/RAG/Memory 明显改善结果时才增加复杂度。

面试口播：

> 我理解 RAG、长上下文和 Memory 不是三个热门词，而是三种不同的信息供给方式。长上下文是一次性看更多，RAG 是先找资料再回答，Memory 是长期保留用户或项目事实。Claude Code 这类 Coding Agent 给我的启发是：代码任务里最重要的 source-of-truth 是当前仓库和测试结果，所以它更强调显式项目记忆、按需读取、上下文压缩和工具权限，而不是把长期记忆完全黑盒化成向量 RAG。ApplyFlow 当前没有做完整 Memory，但如果做，我会先记录用户偏好修正、投递反馈和 bad case，并加上用户隔离、过期和可删除机制。

## 11. RAG 怎么回答

概念回答：

> RAG 解决的是模型参数里没有最新、私有或可追溯知识的问题。它不是让模型更聪明，而是让模型带着可信资料做题。

主流流程：

```text
文档清洗
-> 切分
-> 建索引
-> 混合召回
-> 重排
-> 带引用生成
-> 引用和答案评估
```

评估重点：

- 召回是否覆盖正确资料。
- 引用是否真实准确。
- 上下文是否被噪声污染。
- 答案是否解决用户任务。
- 权限是否正确。

ApplyFlow 防守：

> ApplyFlow 当前没有落地 RAG。未来如果接入，我会优先用于公司资料、岗位政策、面经和历史投递记录，而不是直接替代岗位排序。排序主逻辑仍要靠用户偏好、岗位事实和评估门禁。

一句比喻：

> RAG 像带资料做题，Agent 像拿着资料去办事。很多业务里是 RAG 找证据，Agent 推流程。

业务化回答示例：

> 如果一个知识库问答准确率低，我不会只说“优化 Prompt”。我会先看检索链路：是不是只做向量相似度导致关键词命中差，是不是没有重排，是不是业务场景 Prompt 太泛。一个更完整的方案是混合检索，也就是关键词检索 + 向量检索，再用 rerank 做重排，并按业务场景配置系统 Prompt。上线后看检索准确率、引用命中率、二次追问率、回答采纳率和平均 token 消耗。

顶级项目延伸：

> 很多顶级 Agent 不会把 RAG 当成万能解法。比如 Coding Agent 场景里，代码仓库本身是不断变化的 source-of-truth，向量库如果没有及时更新，反而可能召回旧代码或旧总结。更稳的做法通常是“索引/摘要告诉模型去哪看，模型再用工具读取真实文件”，最后用测试和 diff 验证。这也是为什么我讲 RAG 时不会只讲 embedding，而会同时讲权限、引用、更新频率和评估。

## 12. 长上下文和 RAG 怎么选

概念回答：

> 长上下文解决“放得下”，RAG 解决“找得到”。两者都不自动保证正确。

怎么选：

- 材料少且一次性完整阅读：长上下文。
- 知识库大、经常更新、需要引用和权限：RAG。
- 长任务、多轮任务：RAG + 记忆 + 上下文压缩。

面试句：

> 我不会把整仓库、整知识库都塞进上下文。更稳的方式是先检索关键证据，再把少量高相关内容放进上下文，并保留引用和权限过滤。

ApplyFlow 映射：

- 当前项目文档接手靠 `CONTEXT.md` 和交接文档，不靠模型长记忆。
- 未来历史投递记录和面经更适合用检索，而不是每轮全量塞入。

Claude Code / OpenAI Agents 延伸：

> Claude Code 和 Codex 这类 Coding Agent 的上下文管理很像一个“有规则的工作台”：先有项目规则文件，再有当前任务摘要，再按需读取相关文件，长对话后还要 compact。这样做的原因是代码任务不能只靠模型记忆，必须回到当前文件、命令输出和测试结果。OpenAI Agents 相关资料里也有 progressive disclosure 的思路：先给摘要和索引，必要时再展开细节，避免上下文一开始就被噪声塞满。

## 13. 记忆系统怎么设计

概念回答：

> 记忆不是把聊天历史全部塞给模型，而是决定什么值得记、什么时候取、什么时候忘。

主流设计可以分三类：

| 类型 | 人话解释 | 优点 | 风险 |
|---|---|---|---|
| 规则式记忆 | 人明确写下来的规则、偏好、项目说明，比如 `AGENTS.md`、`CLAUDE.md` | 可控、可审计、不会乱猜 | 需要维护，写太长会污染上下文 |
| 半规则式记忆 | 系统自动总结历史，再用索引或主题文件按需加载 | 适合长任务和跨会话延续 | 摘要可能丢细节或过期 |
| 检索式记忆 | 把历史记录、反馈、文档做检索，按相似度取回 | 适合大量历史材料 | 召回错、权限错、旧信息污染 |

落地时要有：

- 用户隔离：谁的记忆。
- 任务标签：这段记忆属于什么任务。
- 重要性：是否值得长期保存。
- 时间衰减：过期信息不要一直影响模型。
- 检索：按当前任务取相关记忆。
- 权限：不能跨用户、跨项目泄露。
- 可删除：用户可以清理或更正。

ApplyFlow 防守：

> ApplyFlow 当前没有做完整长期记忆。未来如果做，我会优先记录用户偏好修正、投递反馈、拒绝原因和 bad case，但必须有用户隔离、过期机制和可删除能力。

一句洞见：

> 记忆系统真正难的不是存，而是取对、不过度取、不泄露。

Claude Code 延伸：

> 我看到的 Claude Code 公开方案更像“规则式 + 半规则式”的组合：项目可以有显式记忆文件，系统也会做自动 memory 和上下文压缩；长任务里不是把所有历史永远塞进模型，而是保留规则、摘要和关键线索，再让 Agent 按需读文件。它不把记忆完全交给黑盒 RAG，一个重要原因是代码任务要求可追溯和实时 source-of-truth，记忆只能辅助，不能替代当前仓库、命令输出和测试。

面试强化版：

> 如果面试官问 Memory，我会先说它不是聊天记录仓库，而是长期任务里的信息治理。规则式记忆适合项目规则和用户显式偏好，半规则式记忆适合长任务摘要和主题索引，检索式记忆适合大量历史材料。Claude Code 这类工具更强调显式项目记忆、自动 memory、compact 和按需读取，而不是把一切都做成 RAG。因为 coding 场景最怕旧记忆污染当前代码，最终还是要回到当前文件和测试结果。

## 14. 多 Agent 要不要做

概念回答：

> 多 Agent 适合任务复杂、角色边界清楚、需要并行或互相校验的场景。任务还简单时，强行多 Agent 只会增加成本和调试难度。

什么时候用：

- 任务天然分角色：规划、执行、审核、资料检索。
- 子任务可并行。
- 需要互相审查或投票。
- 单 Agent 上下文过长或职责混乱。

什么时候不用：

- 流程可由规则和单 Agent 完成。
- 工具数量少。
- 状态边界还没跑稳。
- 评估和日志还没搭好。

ApplyFlow 防守：

> ApplyFlow 当前用单 Agent + 工作流更稳。未来如果加入简历材料、面试准备、投递跟进和公司资料检索，可以再拆成岗位判断、材料生成、投递执行、复盘分析几个角色。

一句话：

> 多 Agent 是复杂任务的组织方式，不是简历装饰。

## 15. Claude Code / Codex 给你的启发是什么

概念回答：

> 顶级 Coding Agent 的价值不只是模型会写代码，而是围绕模型搭了完整 harness：上下文、工具、权限、任务拆分、会话记录、验证和人工接管。

可以讲的公开启发：

- 上下文管理：不是把所有文件都塞给模型，而是按任务检索、摘要和压缩。
- 工具权限：读、写、执行、网络等动作需要边界。
- 任务拆分：复杂任务要分阶段，必要时用子任务隔离上下文。
- 持久规则：项目规则写进类似 `AGENTS.md` 的持久指令，不靠临场记忆。
- 验证闭环：修改后跑测试、看 diff、做 review。
- 人工接管：高风险操作、删除、发布、合并需要人确认。

不要这么说：

> 我研究过泄露源码，所以知道内部实现。

应该这么说：

> 我只抽象公开资料和公开分析里的工程原则，不引用非公开源码细节。它给我的启发是：Agent 真正的壁垒在 harness，不在单个 Prompt。

ApplyFlow 映射：

- 开发侧：AGENTS.md、CONTEXT.md、TIMELINE.md、验证脚本、Focused Review。
- 产品侧：Agent 输出合同、状态机、权限校验、人工确认、Evidence Log。

一句口播：

> 我把 Coding Agent 的 harness 思路迁移到了 ApplyFlow：模型不直接决定状态，Agent 输出必须结构化、可校验、可降级、可复测。

## 16. 用 Codex 开发怎么保证质量

概念回答：

> 我不会把 Codex 当成事实来源，而是把它当成执行 Agent。它可以提出方案和写代码，但我负责上下文、约束、验证和 review。

我的流程：

1. 先给 Context：当前目标、已知限制、相关文件。
2. 再给 Data：错误日志、接口返回、测试结果。
3. 明确 Expectation：要对比什么、不能改什么、验证什么。
4. 小步修改，不一次性全仓乱改。
5. 跑 smoke 或专项验证。
6. 做 Focused Review，检查正确性和安全边界。

CDE 口播：

> 我用 AI 排查问题时，不是问“帮我修一下”，而是给它 Context、Data、Expectation。这样 AI 才不会乱猜，而是帮我对齐业务规则和工程实现。

## 17. Prompt Engineering、Context Engineering、Harness Engineering 区别

概念回答：

| 概念 | 人话解释 |
|---|---|
| Prompt Engineering | 怎么问模型 |
| Context Engineering | 每轮让模型看什么、看多少、按什么优先级 |
| Harness Engineering | 怎么把模型放进工具、权限、状态、验证和人工接管里 |

面试句：

> Prompt 是输入技巧，Context 是信息组织，Harness 是系统治理。AI 项目上线不能只靠 Prompt，必须有工具权限、状态机、日志、评估和回滚。

ApplyFlow 映射：

- Prompt：岗位解释和风险提示怎么表达。
- Context：岗位事实、用户偏好、历史反馈怎么进入判断。
- Harness：Top10、高优先级候选、地点确认、状态流转、权限校验、Evidence Log。

### Agent Harness Engineering 七层怎么讲

如果面试官问“你理解的 Agent 工程化是什么”，可以把 Harness 拆成七层：

| 层级 | 人话解释 | ApplyFlow / Codex 映射 |
|---|---|---|
| 工具接口与协议 | Agent 能调用什么工具，参数怎么描述和校验 | 插件预填、API 写入、结构化参数、服务端校验 |
| 上下文与记忆管理 | Agent 本轮看什么、长期记什么、怎么压缩 | `CONTEXT.md`、handoff、用户偏好、bad case |
| 生命周期与编排 | 任务怎么规划、执行、暂停、恢复、交接 | 投递清单、状态回填、人工确认、L1/L2/L3 复测 |
| 可观测与运维 | 每一步能不能追踪、定位和优化 | Evidence Log、评估 report、错误日志、production smoke |
| 验证与评估 | 上线前后怎么证明没改坏 | 1000 样本评估、golden set、Focused Review |
| 治理与安全 | 权限、身份、越权、注入、审计 | 400/401/403、source-of-truth、插件不自动提交 |
| 成本与可靠性 | 延迟、token、稳定性、降级和回滚 | 分层评估提速、低风险用规则、高风险人确认 |

口播：

> 我理解的 Harness Engineering 不是只写 eval 脚本，而是 Agent 的运行底座。它包括工具协议、上下文和记忆、任务编排、可观测、验证评估、安全治理和成本可靠性。ApplyFlow 里我把这些落到输出合同、状态机、权限校验、Evidence Log 和分层复测上；Codex 开发侧则落到 AGENTS.md、CONTEXT.md、验证脚本和 Focused Review。

## 18. 模型选型怎么答

概念回答：

> 我不会按排行榜选模型，而是按任务选模型。

选型维度：

- 推理质量。
- 速度。
- 成本。
- 上下文长度。
- 工具调用稳定性。
- 结构化输出能力。
- 合规和可用性。

ApplyFlow 映射：

- 状态枚举、权限校验、非法参数：不用强模型，用规则。
- 岗位语义匹配、推荐解释、bad case 归因：适合模型。
- 插件预填：更看字段映射和用户确认，不看文采。
- 批量评估：要考虑速度和成本，不能每次全量强模型。

一句话：

> 低风险高频任务用规则或便宜模型，复杂推理和关键决策用强模型，高风险执行必须系统校验和人确认。

## 19. AI 产品指标怎么设计

概念回答：

> AI 产品不能只看模型分数，要看收益指标和护栏指标。

收益指标：

- 任务成功率。
- 用户采纳率。
- 操作完成率。
- 时间节省。
- 状态推进率。

护栏指标：

- 错误率。
- 幻觉率。
- 越权率。
- 成本。
- 延迟。
- 人工介入率。

ApplyFlow 指标：

- 投递清单候选率：8.8% -> 16.7%。
- 状态回填率：33.3% -> 58.8%。
- Top10 岗位方向命中：92.4%。
- Top10 城市命中：4.6%，作为下一轮 bad case。
- 插件不自动提交、用户隔离、非法写入拦截作为护栏。

一句洞见：

> 如果回答更自然但业务状态没有推进，或者成本和风险变坏，这个 AI 功能就不算成功。

## 补充三：上线后指标、A/B Test 和失败复盘怎么答

面试官问法：

- 你做 A/B test 时怎么分配流量？
- 用了什么统计检验方法？
- 实验没通过怎么复盘？
- 模型效果跑不通导致项目延期，你怎么沟通？
- 能复盘一次你做烂了或判断失败的 AI 功能吗？

### 上线后主动聊哪些指标

不要只说“准确率提升”。AI 产品上线后要主动补这些指标：

| 指标 | 为什么重要 |
|---|---|
| 人均 token 消耗 | 控制成本，判断是否需要更便宜模型或缓存 |
| 端到端延迟 | 用户是否等得起 |
| 回答采纳率 | 用户是否真的接受 AI 建议 |
| 二次追问率 | 回答是否一次解决，或是否需要反复澄清 |
| 留存或复用率 | 功能是否持续有价值 |
| 人工介入率 | AI 是否减少了人工成本，还是制造了更多复核 |
| 错误建议率 | 护栏指标，避免只看收益 |
| bad case 类型分布 | 下一轮优化方向 |

ApplyFlow 映射：

> ApplyFlow 当前可以讲候选率、状态回填率、Top10 命中、高优先级候选质量和城市 bad case。后续如果线上化，我会补人均 token、推荐采纳率、二次追问率、用户复用率、地点确认触发率和人工介入率。

### A/B Test 怎么说

标准回答：

> 即使只做一周 A/B，也要说清楚流量怎么分、主指标是什么、护栏指标是什么、显著性怎么判断、没通过怎么归因。

面试可用结构：

```text
实验目标：验证什么假设
流量分配：按用户随机或按 session 随机，避免同一用户反复切组
主指标：比如采纳率、候选率、状态回填率
护栏指标：延迟、错误率、成本、投诉、人工介入率
统计方法：样本量够时用比例检验 / 卡方检验；样本量小时不硬说显著，只做方向性复测和 bad case 归因
复盘方式：看分群、漏斗、日志、bad case，不只看总均值
```

ApplyFlow 防守：

> ApplyFlow 目前不是大规模线上 A/B，所以我不会硬说统计显著。我的说法是小样本同口径复测：同一批 5 个测试画像、102 条岗位浏览，对比改版前后候选率和状态回填率。下一步如果有真实用户流量，再做用户级随机分组和显著性检验。

### 实验失败或模型效果不通怎么复盘

回答模板：

> 我会先判断失败发生在哪一层，而不是直接说模型不行。

| 层级 | 怎么排查 |
|---|---|
| 数据层 | 输入数据是否脏、缺字段、过期、分布偏 |
| 模型层 | 意图识别、分类、生成或工具调用是否失败 |
| 规则层 | 业务约束是否过强或过弱 |
| 产品层 | 用户是否看不懂、不会点、缺少确认入口 |
| 工程层 | 缓存、延迟、状态机、权限是否导致错位 |
| 指标层 | 指标是否选错，是否只看均值没看分群 |

ApplyFlow 例子：

> 1000 样本里城市命中只有 4.6%，我没有直接说模型不行，也没有只调权重，而是拆到数据层的地点字段脏、约束层的城市硬/软偏好、优先级层的高优先级降级和交互层的地点确认。这个复盘结果直接变成地点约束修复。L2 复测里，700 个历史误推候选的直接推进率从 100.0% 降到 0.0%，说明 bad case 进入了可验证的回归闭环。

### 算法团队不配合或模型效果导致延期怎么沟通

回答：

> 我不会只说“算法不行”。产品经理要把问题从情绪变成证据：给出样本集、失败类型、业务影响、优先级和可接受的降级方案。

沟通方式：

- 和算法对齐：失败样本、预期输出、可接受阈值、下一轮评估集。
- 和研发对齐：兜底规则、状态机、缓存、灰度和回滚。
- 和业务对齐：延期影响、先上线哪些低风险能力、哪些能力降级为人工确认。
- 和测试对齐：黄金集、边界输入、对抗场景和回归门禁。

面试句：

> 如果模型效果一时跑不通，我会先做降级产品方案，比如把自动结论改成“需确认”、把高风险动作改成人工复核，同时保留日志和 bad case，避免项目完全卡死。

## 20. B 端和 C 端 AI 产品区别

概念回答：

> C 端更看体验、转化和留存；B 端更看流程效率、权限、稳定性、集成成本和 ROI。

C 端：

- 用户是否愿意用。
- 路径是否顺。
- 反馈是否及时。
- 个性化是否明显。

B 端：

- 角色和权限。
- 数据口径。
- 审计和合规。
- 跨系统集成。
- 成本收益。

ApplyFlow 映射：

> ApplyFlow 偏 C 端求职者，所以我看候选率、回填率和主路径清晰度。但如果迁移到企业数据产品或京东商家侧，我会重点看建议采纳率、经营动作完成率、错误建议率、权限和成本。

## 21. 京东或电商 AI 场景怎么答

推荐场景：商家经营分析 + 行动建议。

回答：

> 我会从“看数 -> 解释 -> 建议 -> 执行 -> 复盘”这条链路设计，而不是只做一个聊天入口。

方案：

- 数据入口：商家经营报表、搜索流量、活动、库存、价格、评价。
- AI 判断：解释指标波动，归因活动、价格、库存或流量变化。
- 工作流：把建议变成待办。
- 工具执行：生成活动配置、客服工单、商品优化建议。
- 权限校验：敏感操作需要审批。
- 评估指标：建议采纳率、操作完成率、分析耗时下降、转化改善、错误建议率、成本。

和 ApplyFlow 的迁移关系：

> ApplyFlow 是求职流程里的“判断 -> 清单 -> 执行 -> 复盘”，电商数据产品可以是“看数 -> 建议 -> 执行 -> 复盘”。底层都是 AI 推动业务状态，而不是只生成一段回答。

- 多模态：如果识别网申页面或简历截图，要评估 OCR、字段映射、错误恢复和用户确认。
