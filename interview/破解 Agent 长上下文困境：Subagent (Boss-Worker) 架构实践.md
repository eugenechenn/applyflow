## 🧠内容总结

这篇笔记切中了长上下文 Agent 开发中的一个致命痛点：当项目上下文超出模型窗口时，Agent 会被迫不断生成“交接文档”来压缩记忆，导致陷入“无限阅读准备、永远无法执行”的死循环。作者提出了一种基于 `Subagent` 的主子线程架构（Boss-Worker 模型），通过将“全局监督调度”与“具体任务执行”彻底解耦，并辅以文档化记忆，完美破解了这一工程难题。

## 📌关键信息

- **警惕“压缩交接死循环”**：当单点 Agent 试图同时处理海量信息（Information）和实际动作（Action）时，一旦触及窗口上限，它就会不停地读旧代码、写交接文档给下一个 LLM，导致算力和 Token 全被消耗在“准备工作”上，无法产出实际代码。

- **重新定义主线程（Boss）**：主线程绝不能“干重活”。它的唯一职责是拥有全局记忆、监督进度、协调资源（拆解任务分发下去）。

- **外部化记忆防健忘**：好记性不如烂笔头，必须让主线程把拆解好的清晰 Todo 写进外部文件（如 `readme.md`）中进行状态管理，而不是全塞在 Prompt 里。

- **及时销毁释放资源**：主线程调用完 Subagent 后，需要有销毁/清理机制，防止无用历史信息继续污染上下文。


## 🧩方法/模型（可复用）

**多智能体协作：Boss-Worker (主子分工) 架构模型**

在应对极其复杂的任务时，摒弃“单体全能 Agent”，采用分层架构：

1. **调度层 (Boss Agent / 主线程)**：

    - **输入**：海量的原始项目上下文。

    - **动作**：阅读理解 $\rightarrow$ 提取关键索引 $\rightarrow$ 拆解具体任务清单 (Todo) 并写入 `readme` $\rightarrow$ 唤起 Subagent。

    - **产出**：清晰的任务指令与进度监督，绝不亲自写/改代码。

2. **执行层 (Subagent / 子线程)**：

    - **输入**：由 Boss 喂给的、经过严格裁剪的、仅包含当前任务所需的局部上下文。

    - **动作**：纯粹的执行（Action）。

    - **产出**：提交代码/结果，并向 Boss 汇报后**自行销毁**。

3. **沉淀层 (SOP 持久化)**：

    - 将跑通的协作方法论和规则固化在 `AGENTS.md`（或类似系统提示词库）中，方便系统持续复用，避免每次重新“教”模型怎么做事。
