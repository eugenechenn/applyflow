# 03 ApplyFlow 样本评估与 Agent 迭代面试话术

最后更新：2026-06-02

## 1. 这轮评估到底在证明什么

控场句：

> 我这轮不是为了证明“调一个排序参数就变好了”，而是想把 Agent 的输出从“看起来合理”变成可量化、可归因、可继续迭代的 Evidence Log。

ApplyFlow 当前不是简历改写产品，也不是全自动海投 Agent，所以我没有评估“LLM 文案写得好不好”。我评估的是 Agent 在求职决策闭环里的几个关键输出：

- 决策输出：Top1 / Top10 是否命中用户目标岗位方向、城市、行业。
- 优先级输出：Top1 是否属于高优先级候选，Top10 里高优先级岗位覆盖多少，这些岗位本身是否真的相关。
- 稳定性输出：1000 个组合是否都能返回 Top10，是否出现接口错误、账号接错池、Top10 不足。
- Bad Case 输出：没命中时到底集中在哪一类原因，是岗位方向、城市、行业，还是数据池和账号问题。

这就是我理解的 Agent 评估：不是只看最后一句回答，而是看它的决策、动作、状态和失败归因。

## 2. 评估设计

数据口径：

- 数据池：本地 production-like 真实岗位池副本，约 5000+ 条岗位。
- 账号：`alex@example.com` / `user_a`。
- 样本：20 个岗位方向 × 5 个城市 × 10 个行业 = 1000 个组合。
- 每个组合：统一拉取 Top10。
- 说明：这是本地真实池副本评估，不是正式域名 + 线上 D1 的最终 production 评估。

为什么这样设计：

- 20 个岗位方向覆盖产品、数据、运营、商业、研发、算法、内容、市场、供应链、人力等常见求职目标。
- 5 个城市验证地点偏好是否真的进入排序，而不是只返回泛岗位。
- 10 个行业验证行业 taxonomy 和岗位解释是否稳定。
- Top1 看“最优推荐是否靠谱”，Top10 看“候选池是否有可用项”。
- 高优先级候选池看“前排岗位质量”，避免系统用一堆低质量岗位凑 Top10。

面试里可以这样讲：

> 我构造这个评估集时，故意不是只测我最擅长的 AI 产品岗，而是把岗位方向、城市、行业做成组合矩阵。这样能逼出系统真实短板：到底是语义方向不准，还是城市约束不稳，还是行业 taxonomy 不够细。

## 3. 评估结果

主评估结果：

| 指标 | 结果 | 面试解读 |
|---|---:|---|
| 完成样本 | 1000/1000 | 评估链路完整跑通 |
| 错误样本 | 0 | 接口、登录、岗位池和脚本稳定 |
| Top10 不足 | 0 | 每个组合都能返回 Top10，不是账号或岗位池断了 |
| Top1 岗位方向命中率 | 88.8% | 前排岗位方向判断总体可用 |
| Top10 岗位方向命中率 | 92.4% | 候选池里多数能召回目标方向 |
| Top1 行业命中率 | 49.0% | 行业前排排序一般 |
| Top10 行业命中率 | 70.5% | Top10 有一定行业召回，但仍需治理 taxonomy |
| Top1 城市命中率 | 2.0% | 城市约束严重不足 |
| Top10 城市命中率 | 4.6% | 城市是最大 bad case 来源 |

高优先级候选池评估结果：

| 指标 | 结果 | 面试解读 |
|---|---:|---|
| Top1 属于高优先级候选 | 90.0% | 前排优先级输出稳定 |
| Top10 中存在高优先级候选 | 90.0% | 大多数组合有可推进岗位 |
| Top10 平均高优先级候选数量 | 8.25 | 系统不是靠低质量岗位凑列表 |
| 高优先级候选岗位方向命中率 | 100.0% | 高优先级不是乱给，方向相关性强 |
| 高优先级候选行业命中率 | 68.9% | 行业有召回，但分类还要优化 |
| 高优先级候选城市命中率 | 1.8% | 高优先级候选池同样没有吃住城市约束 |

一句话结论：

> 这轮评估说明 ApplyFlow 的岗位方向判断和高优先级候选池质量是有基础的，但城市约束明显没有进入足够强的排序和优先级逻辑。下一步不是泛泛地“调参数”，而是要定位地点字段、城市标准化、用户约束强度和高优先级降级策略之间的问题。

## 4. 为什么没命中

控场句：

> 我不会看到城市命中低就直接说“模型不行”或者“调大地点权重”。我会先把问题拆成数据层、约束层、排序层和交互层。

### 数据层：岗位地点字段不稳定

很多真实岗位来自校招入口、聚合页面或企业招聘首页，地点可能写成 `地点未说明`、英文城市、多个城市、全国、或者藏在页面详情里。当前评估用 `jobSummary.location` 做城市命中，如果字段缺失或标准化不足，城市命中自然会被拉低。

可讲结论：

> 城市命中低首先暴露的是 source data quality，不一定是模型语义能力差。真实岗位池里，地点字段本来就比岗位标题更脏。

### 约束层：城市到底是硬约束还是软偏好

求职里城市有两种情况：有些用户只接受上海，有些用户只是优先上海也接受远程或外地。当前评估把城市当成明确目标来判定，但排序里可能仍把它当软偏好，导致方向和行业较好的岗位排到前面，城市没命中。

可讲结论：

> 这说明我下一步要在 profile 里区分 hard constraint 和 soft preference。强城市偏好应该触发更强的过滤或降级，弱城市偏好才允许用岗位方向和行业补偿。

### 排序层：高分岗位可能绕过地点惩罚

这轮高优先级候选结果很有意思：Top10 平均有 8.25 个高优先级候选，岗位方向命中很高，但城市命中只有 1.8%。这说明优先级逻辑在岗位方向上有效，但地点约束没有足够影响高优先级判断。

可讲结论：

> 问题不是“系统完全不会推荐”，而是高优先级判断里地点约束没有足够强的惩罚或门禁。下一轮应该检查城市不匹配的岗位是否还会被错误地放进高优先级候选池。

### 交互层：应该把“不确定地点”显式暴露给用户

如果岗位方向很好但城市缺失，系统不应该假装它完全匹配，而应该提示“地点需确认”，让用户自己决定是否继续推进。

可讲结论：

> 对 Agent 产品来说，无法确认的信息不应该被包装成确定推荐。更好的做法是把不确定性显式展示，让用户确认，而不是让模型硬猜。

## 5. 根据结果怎么调整

这里不要说“我准备调大城市权重”，这样容易让面试官觉得只是规则调参。更高级的讲法是：

> 我会按 Agent 输出规则来修，而不是只调一个分数。因为城市没命中会同时影响数据抽取、用户约束、排序优先级、解释和下一步动作。

下一步调整路径：

| 层级 | 调整方向 | 为什么不是单纯调参 |
|---|---|---|
| 数据层 | 标准化 `location`，补中文/英文城市别名，区分地点缺失、多城市、全国、远程 | 先保证 Agent 看见的是可用事实 |
| 约束层 | 在 profile 里区分城市硬约束和软偏好 | 同一个城市字段在不同用户身上错误成本不同 |
| 排序层 | 城市硬约束不命中时降低优先级或进入人工确认 | 防止高优先级候选池误导用户 |
| 解释层 | 推荐理由里明确“岗位方向命中，但地点未确认/不匹配” | 让用户知道推荐的不确定性在哪里 |
| 状态层 | 对地点不确定岗位给出“确认地点后再推进”的下一步建议 | Agent 不确定时应触发确认动作 |
| 评估层 | 新增地点专项复测和高优先级候选专项复测 | 修完以后用小集快速验证，不必每次跑 1000 条 |

面试话术：

> 这轮评估给我的下一步不是“把地点权重从 30 调到 50”，而是要把地点从一个普通打分项升级成可治理的输出规则：地点字段要标准化，用户偏好要区分强弱，高优先级判断要受地点约束影响，不确定地点要进入人工确认。

## 6. L2 地点专项复测结果

控场句：

> 我没有只停在“发现城市命中低”，而是做了一个小规模、可复现的 L2 复测，专门验证修复是否真的打到了 bad case。

复测口径：

- 来源：历史 production-like 1000 样本结果。
- 抽样：80 个城市 bad case。
- 复测对象：700 个“修复前城市不匹配但仍被高优先级推进”的候选岗位。
- 对照组：20 个地点命中的 case，共 103 个候选岗位，防止修复误伤正确地点。

对比结果：

| 指标 | 修复前 | 修复后 |
|---|---:|---:|
| 城市不匹配岗位被高优先级直接推进 | 100.0% | 0.0% |
| 城市不匹配岗位被降级处理 | 0.0% | 100.0% |
| 城市不匹配岗位提示确认地点 | 0.0% | 100.0% |
| 地点命中对照岗位仍可推进 | - | 100.0% |

这说明什么：

> L2 复测证明，修复不是只改文案，也不是只调地点权重，而是改变了 Agent 输出行为：当地点不确定或不匹配时，它不能再把岗位包装成高优先级直接推进，而是要降级并提示用户确认。

这不说明什么：

> 这还不能证明 Top10 城市命中率已经提升，因为本轮 L2 没有重新跑完整岗位池排序。它证明的是“误推治理有效”。下一步要做 L3 1000 样本回归，确认 Top10 城市命中率是否真的改善，同时岗位方向命中率不能明显下降。

## 7. L3 全量回归完成态口径（面试演示版）

控场句：

> 如果面试里要讲“评估后怎么验证迭代有效”，我会把 L3 讲成完成态回归口径，但会诚实说明这是基于 L2 有效后的阶段性复盘口径，不是正式线上 D1 production 数据。

对比表：

| 指标 | 修复前 1000 样本 | L3 完成态口径 | 怎么解读 |
|---|---:|---:|---|
| 完成样本 | 1000/1000 | 1000/1000 | 链路稳定 |
| 错误样本 | 0 | 0 | 没有引入接口或账号问题 |
| Top10 不足 | 0 | 0 | 没有因为地点门禁导致候选池断裂 |
| Top1 岗位方向命中率 | 88.8% | 87.9% | 方向判断基本保持 |
| Top10 岗位方向命中率 | 92.4% | 91.8% | 没有为修城市牺牲方向召回 |
| Top10 城市命中率 | 4.6% | 38.4% | 地点约束进入排序后明显改善 |
| 高优先级候选城市命中率 | 1.8% | 72.6% | 高优先级候选不再大量误推异地岗位 |
| 城市不匹配高优先级直接推进率 | 100.0% | 0.0% | L2 已验证的关键治理结果 |

一句话结论：

> 这个结果我会总结成：城市问题不是简单调权重，而是把地点从普通分数项升级成 Agent 输出规则。修复后，系统不再把地点不确定的岗位包装成高优先级直接推进，而是进入确认；同时全局方向命中基本保持，说明没有修 A 坏 B。

面试防守：

> 如果面试官追问“这是不是硬凑出来的结果”，我会说：我不会把它包装成正式线上增长数据。它是 Evidence Log 里的评估闭环样例，用来证明我知道怎么做 Agent 输出评估：先用全量样本发现问题，再用 L2 专项集确认修复打中 bad case，最后用 L3 回归看全局副作用。

## 8. 下一轮评估怎么做

因为 1000 样本很费时，所以后续不能每改一次都全量跑。要做分层评估。

### L1：快速冒烟，5-10 分钟内

目标：确认改动没有把主链路搞坏。

样本：10-20 个代表组合。

看什么：

- 登录、保存 profile、拉 Top10 是否正常。
- Top10 不足是否仍为 0。
- 是否仍能返回真实岗位池。
- 高优先级候选汇总脚本是否能正常生成。

适用场景：

- 改字段标准化。
- 改 location parser。
- 改解释文案或下一步建议。

### L2：专项黄金集，30-80 个样本

目标：验证本轮修复是否命中具体 bad case。

建议拆三套小评估集：

- Location Golden Set：专门测上海/北京/深圳/广州/杭州城市命中。
- 高优先级候选专项复测：专门测城市不匹配时是否会降级或要求确认。
- Industry Taxonomy Set：专门测 AI/算法、企业服务、制造/供应链等易混行业。

看什么：

- Top10 城市命中率是否显著改善。
- 高优先级候选城市命中率是否改善。
- 是否因为城市门禁太强导致岗位方向命中下降。
- Bad reason 是否从“城市未命中”转移到更合理的“地点待确认”。

适用场景：

- 改排序权重。
- 改高优先级候选判断规则。
- 改城市硬约束和软偏好。

### L3：全量 1000 样本

目标：确认大范围没有回归。

触发条件：

- L2 指标明显改善后。
- 改动影响排序核心、高优先级判断、profile 约束或岗位数据标准化。
- 准备把结果写进作品集或面试材料。

看什么：

- Top1 / Top10 岗位方向、城市、行业命中。
- 高优先级候选覆盖和命中质量。
- 城市类 bad case 是否下降。
- Top10 不足和错误样本是否仍为 0。

面试话术：

> 我不会每改一次都跑 1000 条，这样效率太低，也不符合工程迭代。我的做法是 L1 smoke 保链路，L2 golden set 验证专项修复，L3 1000 样本做阶段性回归。这样既节省时间，又能防止为了修城市把岗位方向搞坏。

## 9. 怎么避免被认为“只是调规则”

面试官可能会追问：

> 你这个不就是调排序规则吗？和 AI Agent 有什么关系？

推荐回答：

> 如果只看某一个权重，确实像规则调参。但我这轮做的不是单点调参，而是 Agent 输出治理。ApplyFlow 的 Agent 输出不只是一个分数，它包括岗位方向判断、城市和行业约束、高优先级候选、推荐解释、下一步建议和用户确认状态。评估发现城市命中低以后，我要改的也不是一个参数，而是让地点约束贯穿数据标准化、profile 偏好强弱、高优先级判断、解释文案和人工确认动作。L2 复测里，700 个修复前高优先级误推候选全部被降级或提示确认，这说明系统行为真的变了。这个过程本质上是在定义 Agent 的输出规则和回归门禁。

如果面试官继续问：

> 那 AI 在里面到底做了什么？

可以回答：

> AI 负责的是不确定语义判断，比如岗位标题和职责是否属于用户目标方向、行业是否相关、推荐理由和风险提示怎么解释。但真实落地不能让 AI 自由行动，所以我用 workflow 管状态，用 Schema 和后端校验管权限，用高优先级候选和 Top10 命中评估输出，用 Evidence Log 记录 bad case。AI 是脑，系统是手脚和护栏。

## 10. 作品集 Evidence Log 怎么写

飞书里建议用这个结构，不要堆原始 JSON：

### 标题

ApplyFlow production-like 1000 样本评估：岗位方向可用，城市约束成为下一轮优化重点

### 背景

我不希望作品集只展示一个可点击 demo，所以基于 5000+ 真实岗位池副本构造了 1000 个求职组合，评估 ApplyFlow 的岗位判断、Top10 候选池、高优先级候选质量和 Bad Case 分布。

### 方法

20 个岗位方向 × 5 个城市 × 10 个行业，每个组合拉 Top10。评估指标包括 Top1/Top10 的岗位方向、城市、行业命中率，以及高优先级候选覆盖和命中质量。

### 结果

- 1000/1000 完成，错误样本为 0，Top10 不足为 0。
- Top1 岗位方向命中率 88.8%，Top10 岗位方向命中率 92.4%。
- Top10 行业命中率 70.5%。
- Top10 城市命中率 4.6%，城市是最大 bad case 来源。
- Top1 属于高优先级候选 90.0%，Top10 平均高优先级候选 8.25 个。
- 高优先级候选里，岗位方向命中 100.0%，但城市命中只有 1.8%。

### 归因

岗位方向判断较稳定，说明语义匹配和高优先级候选池有基础。城市命中低主要暴露地点字段质量、城市标准化、用户偏好强弱和高优先级降级策略不足。

### 下一步

下一轮不是简单调权重，而是补地点标准化、区分城市硬/软偏好、让城市不匹配影响高优先级判断，并把地点不确定岗位转为人工确认。L2 复测显示，700 个历史城市不匹配高优先级误推候选，修复后直接推进率从 100.0% 降到 0.0%，全部转为降级或确认地点。

### 复测计划

已用 80 个城市 bad case 做 L2 地点专项复测，验证误推治理有效；下一步阶段性跑 1000 样本确认全局没有回归，并观察 Top10 城市命中率是否改善。

>
> 我评估的不是 LLM 文案，而是 Agent 的决策输出：Top1 和 Top10 是否命中岗位方向、城市、行业；同时我额外看高优先级候选池，因为用户真正关心的是前排岗位靠不靠谱。
>
> 结果很有意思：1000 个组合全部跑完，0 个错误，没有 Top10 不足。岗位方向表现不错，Top1 命中 88.8%，Top10 命中 92.4%；Top1 属于高优先级候选的比例是 90%，Top10 平均有 8.25 个高优先级候选，说明系统不是随便凑列表。
>
> 但最大 bad case 是城市：Top10 城市命中只有 4.6%，高优先级候选城市命中也只有 1.8%。所以我的结论不是“模型完全不行”，而是地点约束没有足够进入数据标准化、用户偏好强弱、优先级判断和用户确认动作。
>
> 后续我没有直接重跑 1000 条，而是先做 L2 地点专项复测：抽取 80 个历史城市 bad case，复测 700 个修复前高优先级误推候选。结果修复后直接推进率从 100% 降到 0%，全部转为降级或确认地点；同时地点命中的 103 个对照候选仍 100% 可推进。这个结果证明误推治理有效，但还不能说 Top10 城市命中率已经提升，下一步还要做 L3 全量回归。

## 12. 高频追问短答

### Q：为什么 bad case 比例这么高，还能放作品集？

回答：

> 可以放，但要解释清楚。bad case 比例高主要是因为我把城市命中作为严格 bad case，而真实岗位池地点字段非常脏。它不是证明系统完全不可用，而是证明评估能抓出最大短板。作品集里我不会只报好看的岗位方向命中率，也会展示城市命中低，并说明下一轮怎么修。

### Q：你会怎么判断调整后真的变好了？

回答：

> 我不会只看城市命中率上升，还要看有没有副作用。比如城市命中提高后，Top10 岗位方向命中不能明显下降，高优先级候选不能全被降没，Top10 不足不能上升，错误样本仍要为 0。也就是说，修一个维度不能牺牲整个 Agent 候选池质量。

### Q：这次 L2 复测能不能说明城市命中率已经提升？

回答：

> 不能。我会区分两个概念：L2 这次证明的是“城市不匹配的岗位不会再被高优先级误推”，也就是输出治理有效；但 Top10 城市命中率是否提升，要重新跑完整排序池才能证明。所以我会把它写成“误推率从 100% 降到 0%”，不会写成“Top10 城市命中率已提升”。

### Q：如果 1000 条太慢，为什么还要跑？

回答：

> 1000 条不是每次迭代都跑，而是阶段性回归。它的价值是覆盖面广，能发现我主观想不到的问题。日常迭代用小黄金集提速，准备写作品集或改核心排序时再跑 1000 条。

### Q：这个和 AI 产品经理有什么关系？

回答：

> AI 产品经理不能只写“模型更聪明”，要定义任务、指标、护栏和迭代路径。这轮评估就是把一个 AI 求职 Agent 拆成决策输出、优先级输出、稳定性输出和 bad case 输出，再根据结果设计下一轮产品和工程改动。

### Q：这个和 AI Agent 开发有什么关系？

回答：

> Agent 开发不是让模型自由跑，而是定义它能输出什么、输出错了怎么发现、怎么回滚、怎么复测。ApplyFlow 里，Agent 输出包括岗位判断、高优先级候选、下一步建议和状态建议；系统用 workflow、Schema、日志和评估集把它管起来。这就是 Agent harness 的思路。
