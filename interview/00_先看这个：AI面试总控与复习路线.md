# 00 AI Agent 面试母题地图

最后更新：2026-06-03

## 1. 先说结论

不要再按一堆散题背。AI Agent 岗位面试看起来问题很多，其实大多会落到 8 个母题：

1. 意图识别与任务拆解。
2. 上下文管理、记忆机制与 RAG。
3. 工具调用、权限与协议。
4. 多智能体与任务编排。
5. Agent 评测、Tracing 与 Harness。
6. AI Coding / Coding Agent。
7. AI 产品上线、指标、A/B 与失败复盘。
8. 项目深挖：从简历和作品集追问真实细节。

你的背法不是“每题背一段”，而是每个母题背一个回答骨架。面试官换问法时，只是入口不同，最后都接回同一套逻辑。

## 2. 通用回答结构

每道题都用这个结构，不要一上来背 ApplyFlow：

```text
概念：先用人话解释这个技术解决什么问题
主流做法：讲行业里通常怎么做，最好能对比 Claude Code / OpenAI Agents / Anthropic
项目映射：只有 ApplyFlow 真做过或面试官追问项目时才接项目；没问项目就自然讲知识点
评估与边界：怎么验证、有什么风险、下一步怎么补
```

一句提醒：

> 面试官不是只想听你知道某个名词，也不是想听你把所有题都硬扯回 ApplyFlow，而是看你能不能说清楚这个技术解决什么问题、关键风险在哪里、线上怎么兜底。

## 短期复习优先级

不要先背 60 道题。短期先背 7 个“能展开”的口播，每个控制在 30-60 秒：

1. Agent 和 workflow 的区别。
2. RAG、长上下文、Memory 的区别。
3. 工具调用错参、越权和超时怎么办。
4. Agent 怎么评估，tracing 要看什么。
5. Claude Code / Codex 给你的启发。
6. AI 产品最大局限和不确定性怎么产品化。
7. ApplyFlow 的 Agent 输出评估和城市 bad case。

背法：

> 先说一句人话概念，再说 2-3 个关键工程点，最后如果和 ApplyFlow 有关再接项目证据；如果无关，就停在知识理解和风险边界，不要硬接项目。

## 高频追问速查：只扫不背

这部分是网页高频题和帖子经验整理后的“出题入口”。不要逐题背，先判断它落在哪个母题，再用 30-60 秒口语回答。

| 方向 | 高频追问 |
|---|---|
| 意图识别与任务拆解 | Agent 和 workflow 区别是什么；ReAct 和 Plan-and-Execute 怎么选；为什么有些场景不用 Agent；用户目标模糊时怎么澄清；意图识别错了怎么兜底；Prompt 分类和微调分类怎么选 |
| 上下文与记忆 | RAG、长上下文、Memory 区别是什么；为什么 Claude Code 不简单依赖 RAG；上下文太长怎么压缩；多轮对话重启后状态怎么保留；记忆怎么做用户隔离；旧记忆污染当前结果怎么办 |
| 工具调用与协议 | Tool Calling 参数错了怎么办；MCP 是什么；工具描述怎么写；工具权限怎么控；Prompt 注入怎么防；工具调用超时、失败、重试怎么设计 |
| 后端稳定性与成本 | Agent 调 API 有时 1 秒、有时 10 秒怎么办；怎么做限流熔断降级；模型调用太贵怎么降成本；请求合并和结果缓存怎么做；异步任务怎么恢复；分布式缓存和状态持久化怎么做 |
| 多智能体编排 | 什么时候拆 Planner/Executor/Reviewer；多 Agent 怎么避免互相甩锅；单 Agent 和多 Agent 成本怎么比；任务并行怎么合并结果；审查 Agent 怎么评估；什么时候不要多 Agent |
| Agent 评测与 Harness | 没有大段文本输出怎么评估；LLM-as-a-Judge 靠不靠谱；Eval Harness 怎么搭；Tracing 要记录什么；线上 bad case 怎么回流；怎么防止修 A 坏 B |
| AI Coding | Codex/Claude Code 给你什么启发；AI 写代码怎么保证质量；长对话怎么不跑偏；为什么 coding agent 要读真实文件而不是靠记忆；权限、测试、review 怎么设计；怎么处理错误 patch |
| 产品上线与复盘 | AI 产品最大局限是什么；A/B test 没过怎么办；上线看哪些指标；算法团队延期怎么办；用户不信 AI 怎么办；冷启动没有数据怎么办；怎么设计人工确认和置信提示 |

一句控场：

> Agent 开发岗不是只考 Prompt，而是看你能不能把模型、工具、API、状态、成本、评测和产品边界串起来，并且在线上不崩。

## 3. 母题一：意图识别与任务拆解

常见问法：

- Agent 和 workflow 有什么区别？
- 为什么你的项目算 Agent？
- ReAct、Plan-and-Execute 怎么选？
- 如果做 AI 客服 / 招聘助手 / 数据助手，你怎么设计？

核心回答：

> Agent 不是“模型自由行动”，而是在目标不确定、需要调用工具、需要多步推进时，由模型负责判断和选择；workflow 则负责确定流程、状态和边界。真实落地一般不是纯 Agent，而是 Agent + workflow：模型处理不确定判断，系统管确定执行。

主流延伸：

- Anthropic 的 effective agents 思路是先用简单 workflow，只有复杂度真的带来收益时才加 Agent。
- OpenAI Agents SDK 更强调工具、handoff、guardrails、tracing 和 eval，而不是只让模型聊天。

ApplyFlow 映射：

> ApplyFlow 的 Agent 性不在单个排序函数，而在“判断 -> 清单 -> 执行辅助 -> 状态回填 -> 反馈复盘”的闭环。AI 判断岗位方向、风险和下一步建议；系统管理投递清单、状态和权限；用户确认高风险动作。

## 4. 母题二：上下文、记忆与 RAG

常见问法：

- RAG 和长上下文怎么选？
- Agent memory 怎么设计？
- Claude Code 为什么不简单依赖 RAG？
- 上下文太长、历史太多怎么处理？

核心回答：

> 长上下文解决“这次能看多少”，RAG 解决“去哪找资料”，Memory 解决“哪些历史值得长期留下”。三者经常组合，但不能互相替代。

主流分型：

| 类型 | 人话解释 | 适合什么 | 风险 |
|---|---|---|---|
| 长上下文 | 本轮直接塞更多材料 | 合同、简历、长报告、少量代码 | 成本高、噪声多 |
| RAG | 先检索，再带证据回答 | 企业知识库、政策、面经、历史记录 | 召回错、引用错、旧资料污染 |
| 规则式记忆 | 人写下来的规则和偏好 | 项目规范、用户显式偏好 | 需要维护 |
| 半规则式记忆 | 系统总结历史，再按任务加载 | 长任务、跨会话接力 | 摘要可能过期 |
| 检索式记忆 | 历史记录做索引后检索 | 大量历史反馈 | 权限和召回风险 |

顶级项目延伸：

> Claude Code 公开文档更像“规则式 + 半规则式”组合：项目有显式记忆文件，系统有自动 memory 和 compact，长任务不是把所有历史一直塞进去，而是保留规则、摘要和关键线索，再按需读取真实文件。原因是代码任务的 source-of-truth 是当前仓库和测试结果，旧 RAG 召回反而可能污染判断。

ApplyFlow 防守：

> ApplyFlow 当前没有做完整长期 Memory。如果后续做，我会先记录用户偏好修正、投递反馈、拒绝原因和 bad case，并加用户隔离、过期、可删除和复测机制。RAG 更适合公司资料、岗位政策、面经和历史投递，不会直接替代岗位排序主逻辑。

## 5. 母题三：工具调用、权限与协议

常见问法：

- Tool Calling 参数错了怎么办？
- MCP / LangGraph / AutoGen 怎么看？
- Prompt 注入怎么办？
- 为什么不全自动投递？

核心回答：

> 工具调用不能靠模型自觉。Prompt 是软约束，真正可靠的是参数 schema、权限、状态机、日志和人工确认。

主流做法：

- 工具有清晰描述和参数 schema。
- 工具调用前检查权限和状态。
- 外部网页、用户输入、历史记忆都当作不可信输入。
- 高风险动作要审批或人工确认。
- 记录工具调用轨迹，方便失败归因。

ApplyFlow 映射：

> ApplyFlow 的 Edge 插件只辅助预填官网可识别字段，不自动提交、不绕过验证码、不处理复杂附件。服务端不信前端传来的用户身份，非法参数 400，未登录 401，越权 403。

## 6. 母题四：多智能体与编排

常见问法：

- 什么时候用多 Agent？
- 什么时候不用多 Agent？
- Planner / Executor / Reviewer 怎么拆？

核心回答：

> 多 Agent 是复杂任务的组织方式，不是简历装饰。只有当任务角色清楚、可并行、需要互相校验，或者单 Agent 上下文太乱时，才值得拆。

自然回答：

> 我不会为了显得高级强行多 Agent。任务还没跑稳时，单 Agent + workflow 更容易控制；只有当角色边界清楚、可并行、需要互相校验，或者上下文太乱时，才值得拆 Planner、Executor、Reviewer 这类角色。

## 7. 母题五：Agent 评测、Tracing 与 Harness

常见问法：

- 怎么评估 Agent？
- 没有 LLM 文本输出怎么判断对不对？
- Eval Harness 怎么搭？
- 什么是 Harness Engineering？

核心回答：

> Agent 输出不只有文本，也包括决策、工具调用、状态变化和下一步动作。评估时不能只看“有没有返回结果”，要看终态结果、过程轨迹、系统成本和安全边界。

Agent Harness 七层：

| 层级 | 人话解释 |
|---|---|
| 工具接口 | Agent 能调用什么，参数怎么校验 |
| 上下文记忆 | 本轮看什么，长期记什么 |
| 生命周期编排 | 任务怎么开始、暂停、恢复、交接 |
| 可观测 | 每一步能不能追踪 |
| 验证评估 | 上线前后怎么证明没改坏 |
| 治理安全 | 权限、身份、越权、审计 |
| 成本可靠性 | 延迟、token、降级和回滚 |

ApplyFlow 映射：

> ApplyFlow 的评估不是看模型文案，而是看 Top10 排序、高优先级候选、推荐解释、下一步建议和状态变化。1000 样本评估发现岗位方向可用，但城市是最大 bad case；L2 复测验证 700 个历史城市不匹配高优先级误推候选，修复后直接推进率从 100.0% 降到 0.0%。

## 8. 母题六：AI Coding / Coding Agent

常见问法：

- Codex / Claude Code 给你什么启发？
- 用 AI 写代码怎么保证质量？
- 长对话怎么防止越改越乱？

核心回答：

> Coding Agent 的壁垒不是“模型会写代码”，而是有没有 harness 管住上下文、工具权限、任务拆分、会话记录、验证和人工接管。

ApplyFlow / Codex 映射：

- `AGENTS.md`：项目规则和边界。
- `CONTEXT.md`：当前工作现场。
- `TIMELINE.md`：阶段变化留痕。
- 验证脚本：smoke、专项验证、gate。
- Focused Review：检查正确性和安全边界。

面试句：

> 我把 Coding Agent 的 harness 思路迁移到产品侧：Agent 输出也要有规则、门禁和复测，不能让模型直接决定真实状态。

## 9. 母题七：AI 产品上线、指标、A/B 与失败复盘

常见问法：

- AI 产品最大局限是什么？
- 上线后看什么指标？
- A/B test 没通过怎么办？
- 算法团队不配合或模型效果延期怎么办？

核心回答：

> 我觉得 AI 产品最大的局限不是简单“模型会幻觉”，而是不确定性没有被产品化。模型不确定时，产品要给用户信号，比如证据引用、置信提示、二次确认、联网搜索或人工复核。

上线指标：

- 任务完成率。
- 用户采纳率。
- 二次追问率。
- 人均 token 消耗。
- 端到端延迟。
- 人工介入率。
- 错误建议率。
- bad case 类型分布。

失败复盘：

> 我不会直接说模型不行，而是分层排查：数据层、模型层、规则层、产品层、工程层、指标层。ApplyFlow 的城市问题就是这样拆的：地点字段脏、城市硬/软偏好不清、高优先级降级不足、地点不确定没有提示用户确认。

- 城市命中这么低为什么能放作品集？
- 为什么不做简历改写？
- 你有没有伪造数据？

核心回答：

> ApplyFlow 的价值不是证明系统完美，而是证明我能做评估闭环：发现问题、归因、修复输出规则、专项复测、再决定是否全量回归。

必须诚实：

- 1000 样本是本地真实岗位池副本，不是正式线上 D1 production。
- L2 复测证明“城市不匹配高优先级误推”被治理，不证明 Top10 城市命中率已经提升。

## 12. 最小背诵卡

1. Agent 不是自由行动，而是不确定判断进入确定流程。
2. 长上下文看得多，RAG 找资料，Memory 留历史。
3. 工具调用不能靠 Prompt，要靠 schema、权限、状态机和日志。
4. 多 Agent 是复杂任务组织方式，不是简历装饰。
5. Agent 评估看结果、过程、成本和安全，不只看文本。
6. Coding Agent 的核心是 harness，不是模型会写代码。
7. AI 产品要把不确定性产品化，低置信度时提示确认。
8. 失败复盘要分数据、模型、规则、产品、工程、指标层。
9. ApplyFlow 当前可讲真实证据：1000 样本 + L2 误推治理。
10. 没跑完 L3 前，不伪造成全量复测结果。
