# 01 ApplyFlow 项目面试主线

最后更新：2026-06-02

## 1. 30 秒介绍

ApplyFlow 是我做的一个求职决策与执行闭环 Agent / Agent workflow 原型。它不是全自动海投，也不是简历改写工具，而是解决求职者在“岗位太多、不知道先投哪个、投完以后容易断档”这个流程问题。

我的设计是：AI 负责岗位语义判断、推荐解释和风险提示；系统负责投递清单、状态回填、权限校验和日志；Edge 插件只在用户确认后辅助预填官网可识别字段，最终提交仍由用户自己确认。

所以我想证明的不是“模型会聊天”，而是 AI 能不能被放进一个有边界、有指标、有反馈的真实任务流程里。

## 2. 3 分钟完整故事

我做 ApplyFlow 的起点不是想接一个大模型接口，而是求职流程里很具体的断点：岗位很多，用户不知道哪些值得优先投；点开官网投递链接后，系统记录容易断掉；投完以后，状态和反馈也很难沉淀。

所以我没有先做最容易展示的简历改写或求职信生成，而是先做一条更能验证的执行链路：

```text
岗位导入
-> 用户偏好建模
-> 可解释排序
-> 投递清单
-> 官网投递链接
-> Edge 插件辅助预填
-> 用户确认提交
-> 状态回填
-> 用户反馈 / Bad Case
-> Evidence Log 复测
```

这条链路里的关键取舍是“AI 做脑，系统做手脚，高风险动作人确认”。岗位方向、行业、地点、推荐理由这些不确定判断交给 AI；投递状态、用户归属、写入权限这些确定性规则交给系统；自动提交、验证码、附件上传这些高风险动作不交给黑盒。

我用小样本走查和 1000 样本评估来证明这个项目不是只会展示 Demo。小样本里，投递清单候选率从 8.8% 提升到 16.7%，状态回填率从 33.3% 提升到 58.8%。1000 样本里，Top1 岗位方向命中 88.8%，Top10 方向命中 92.4%，但城市命中很低。这个结果反而帮我定位了下一轮核心问题：城市约束没有进入完整的 Agent 输出合同。

## 3. 简历和作品集被深挖时的主线

### 面试官看到的简历事实

- 华南理工大学国际工商管理专业，另有通信工程本科背景。
- 网易 AIGC 内容安全策略运营实习，参与样本抽检、风险分类、Prompt 测试样例和 Bad Case 记录。
- ApplyFlow 项目写了 AI Agent Workflow、评估、结构化输出、人机协同边界、可解释排序和回归验证。

### 你要主动传达的能力

- 我不是算法训练型候选人，但我能把 AI 能力放进真实业务流程。
- 我不是只会调 Prompt，而是会定义输出合同、评估口径、用户边界和工程门禁。
- 我不是只展示好结果，也敢把城市命中低这种 bad case 放进 Evidence Log 并说明下一轮怎么修。

## 4. 项目最强回答：怎么评估 Agent 输出

面试官问法：

- 你怎么评估 Agent 输出？
- 你的项目没有大段 LLM 文本，怎么证明 Agent 有用？
- 1000 样本评估到底说明什么？
- 城市命中这么低，为什么还能放作品集？

标准回答：

> 我评估 Agent 输出时，不只看它有没有返回 Top10，而是看结构化输出是否符合用户目标。ApplyFlow 里 Agent 输出包括 Top10 排序、高优先级候选、推荐解释和下一步动作。
>
> 这轮 1000 样本评估里，岗位方向表现不错，Top1 方向命中 88.8%，Top10 方向命中 92.4%；高优先级候选岗位方向命中也很高。但城市命中很低，Top10 城市命中只有 4.6%，高优先级候选城市命中只有 1.8%。
>
> 我的判断不是“模型完全不行”，而是城市约束没有进入完整的 Agent 输出规则。也就是说，系统知道岗位方向相关，但没有充分处理地点字段脏、城市硬/软偏好、高优先级降级和地点不确定提示。
>
> 下一步我会先做地点标准化，再区分城市硬约束和软偏好；如果硬约束不命中，就不能继续作为高优先级直接推进，而要降级或提示用户确认地点。后续 L2 复测里，700 个历史误推候选的直接推进率已经从 100.0% 降到 0.0%；最后还要阶段性再跑 1000 样本防止全局回归。
>
> 所以这不是简单调规则，而是把 Agent 的输出从“给一个看似合理的岗位列表”，升级成“可解释、可降级、可确认、可复测”的决策系统。

更口语的 30 秒版：

> 我不只看 Agent 有没有返回列表，而是看它的排序、优先级、解释和下一步动作是不是符合用户目标。1000 样本里，岗位方向是可用的，Top10 方向命中 92.4%；但城市命中只有 4.6%。所以问题不在于模型完全没用，而是地点没有变成完整输出规则。下一步我会让城市硬约束影响高优先级判断和确认动作，再用专项黄金集复测。

## 5. 为什么这是 Agent workflow，不只是排序规则

先承认：

> 如果只看一个排序函数，确实不能硬叫 Agent。

再解释：

> ApplyFlow 的 Agent 性不在单个分数，而在一条闭环：AI 做岗位语义判断和推荐解释；系统把判断转成投递清单、状态回填和反馈记录；插件辅助官网预填；用户反馈再回到 Bad Case 和 Evidence Log。它不是模型自由行动，而是 Agent 判断被 workflow、权限和评估机制管住。

项目映射：

| 环节 | ApplyFlow 怎么做 |
|---|---|
| 决策 | 岗位方向、行业、地点、公司类型、投递可行性判断 |
| 控制 | 高优先级候选、是否建议推进、地点确认、状态枚举 |
| 动作 | 加入投递清单、打开投递链接、插件辅助预填、状态回填 |
| 反馈 | 不匹配、误判、已投递、Bad Case、Evidence Log |

## 6. 为什么不全自动海投

回答：

> 我不是做不到自动化，而是不会把高风险动作交给黑盒。求职投递会影响真实机会、个人材料和外部平台规则，错误成本比普通推荐高很多。

ApplyFlow 的边界：

- AI 可以建议哪个岗位值得投。
- 系统可以生成投递清单和状态记录。
- 插件可以在用户触发后预填稳定字段。
- 最终提交、验证码、附件、复杂多步骤流程必须用户确认。

一句洞见：

> AI 产品不是自动化越多越好，而是低风险动作提效，高风险动作留人确认。

## 7. 为什么没先做简历改写

回答：

> 完整自动求职 Agent 当然可以包括简历解析、JD 分析、简历改写、求职信、投递和跟进。但我没有先做简历改写，是因为它主观性强、事实错误成本高，而且很容易变成“文案看起来不错，但流程有没有推进不知道”的 Demo。

ApplyFlow 当前先验证更客观的切片：

- 岗位是否命中目标方向。
- 用户是否愿意加入投递清单。
- 投完是否愿意回填状态。
- 错误是否能进入 Bad Case 和复测。

防守句：

> 我不是不知道简历改写这条链路，而是先做更容易被指标和状态验证的执行切片。后续如果做简历改写，我会先补事实一致性、版本记录、用户确认和投递反馈回流。

## 8. 1000 样本评估怎么讲

口径：

- 本地真实岗位池副本，不是正式线上 D1 production 结果。
- 5000+ 岗位。
- 20 个岗位方向 × 5 个城市 × 10 个行业 = 1000 个组合。
- 每个组合拉 Top10。
- 看岗位方向、城市、行业、高优先级候选和 bad case。

主结果：

| 指标 | 结果 | 面试解释 |
|---|---:|---|
| 完成样本 | 1000/1000 | 评估链路完整跑通 |
| 错误样本 | 0 | 登录、接口和岗位池稳定 |
| Top10 不足 | 0 | 每个组合都能返回候选池 |
| Top1 岗位方向命中 | 88.8% | 前排方向判断可用 |
| Top10 岗位方向命中 | 92.4% | 候选池能召回目标方向 |
| Top10 行业命中 | 70.5% | 行业召回有基础 |
| Top10 城市命中 | 4.6% | 城市是最大 bad case |

高优先级候选结果：

| 指标 | 结果 | 面试解释 |
|---|---:|---|
| Top1 属于高优先级候选 | 90.0% | 前排优先级输出稳定 |
| Top10 平均高优先级候选数量 | 8.25 | 不是靠低质量岗位凑列表 |
| 高优先级候选岗位方向命中 | 100.0% | 高优先级候选池方向相关 |
| 高优先级候选城市命中 | 1.8% | 地点约束没有吃进优先级判断 |

一句结论：

> 这轮评估不是为了证明系统完美，而是证明我能把 Agent 输出量化、归因，并把 bad case 转成下一轮输出合同。

## 9. 地点约束修复怎么讲

概念：

> 输出规则就是系统承诺 Agent 输出必须包含哪些可校验信息，以及这些信息如何影响动作。不是模型说一句“推荐你投”，而是要能落到优先级、状态、解释和下一步动作。

ApplyFlow 第一轮修复：

| 地点情况 | 系统动作 |
|---|---|
| 地点符合偏好 | 可以作为高优先级候选推进 |
| 地点不符合偏好 | 提示确认地点后再推进 |
| 地点未说明 | 不当成 0 分误杀，提示确认岗位地点 |
| 全国/多地范围 | 提示确认是否覆盖目标城市 |

面试句：

> 地点不匹配不是简单扣分，而是影响是否给高优先级、是否建议推进和下一步动作。这就是我说的 Agent 输出规则治理。

## 10. Codex / Claude Code / Coding Agent 怎么接到项目

不要说：

> 我看过某某泄露源码，所以知道内部怎么写。

应该说：

> 我关注的是这些顶级 Coding Agent 暴露出的工程原则：真正的壁垒不是单个 Prompt，而是围绕模型搭建运行底座，包括上下文管理、工具权限、任务拆分、会话记录、验证脚本和人工接管。

映射到 ApplyFlow / Codex 开发：

- `AGENTS.md`：把项目规则、编码、验证、review 边界写成持久上下文。
- `CONTEXT.md`：让新会话快速恢复现场，不靠模型记忆。
- 验证脚本：让 AI 改动必须通过 smoke 或 gate。
- Focused Review：不只看代码正确，还看权限、缓存、source-of-truth 和相邻流程。
- 人工确认：高风险动作不让模型直接决定。

一句口播：

> Claude Code 这类工具给我的启发是：Coding Agent 的核心不是“模型能写代码”，而是有没有 harness 把它关进可验证流程里。ApplyFlow 里我把同样思路迁移到产品侧，Agent 输出也要有合同、门禁和复测。

## 11. 网易实习怎么和 ApplyFlow 串起来

回答：

> 网易 AIGC 内容安全实习让我更早接触到 AI 输出的不确定性。AIGC 内容看起来流畅，不代表事实、安全和策略都没问题，所以需要样本抽检、风险分类、Bad Case 台账和人工复核。

和 ApplyFlow 的联系：

- 网易：治理 AIGC 内容风险。
- ApplyFlow：治理 Agent 决策风险。
- 共同点：不能只信模型输出，要有分类、抽检、反馈和复测。

一句总结：

> 我把网易实习里的 Bad Case 和策略治理思路，迁移到了 ApplyFlow 的岗位推荐、状态边界和 Evidence Log 里。

## 12. 当前不足与下一步

当前不足：

- 真实用户样本还小，小样本指标不是大规模增长。
- 1000 样本是本地真实池副本，不是正式线上 D1 production 账号结果。
- 城市约束第一轮已做地点约束修复验证，并已完成 L2 误推治理复测；但还没完成阶段性全量复测，不能直接宣称 Top10 城市命中率已提升。
- 正式自定义域名还需要切换。
- 简历改写、RAG、多 Agent、模型训练都没有落地。

下一步：

- 阶段性跑 L3 1000 样本，验证 Top10 城市命中率是否改善。
- 正式域名恢复后，再跑线上 production 账号评估。
- 把朋友试用截图、匿名原话、bad case 修复前后对比补进飞书作品集。

## 14. Focused Review 自审记录

Correctness Findings：

- 已将 ApplyFlow 主线重构为面试官从简历和作品集深挖时可直接口播的结构。
- 已保留项目定位、小样本指标、1000 样本评估、高优先级候选指标、地点约束修复和当前不足。
- 已把用户认可的 Agent 输出评估回答升级为本文件核心回答。

Boundary/Safety Findings：

- 未把 ApplyFlow 写成全自动投递、简历改写、RAG、多 Agent 或模型训练项目。
- 未把本地真实池副本评估写成正式线上 production 结果。
- Claude Code 相关内容只表达公开工程原则，不引用非公开源码细节。

Adversarial Scenarios Checked：

- 检查“只是排序规则”“为什么不全自动”“为什么没做简历改写”“城市命中低为什么能放作品集”都有防守回答。
- 检查高风险动作都回到用户确认和系统门禁。
- 检查指标都注明口径和限制。

Blast Radius & Adjacent Regression Assessment：

- 本轮只改面试文档，不改产品代码、数据库、部署或评估脚本。

Residual Risks：

- 仍需用户按自己的语气练习，把长答案压缩成 30 秒和 90 秒两个版本。
