# ApplyFlow 简历修改与作品集材料方案

最后更新：2026-05-16

## 1. 当前简历诊断

当前简历的优势：

- 有华南理工 MBA / 工商管理背景，适合 AI 产品、AI 运营、AI 应用落地方向。
- 有网易 AIGC 内容安全策略运营实习，可和 ApplyFlow 的 Bad Case、AI 边界、人机协同、反馈复盘形成连续叙事。
- 有销售管理、客户运营、项目管理、企业诊断经历，能支撑“业务理解 + 用户反馈 + 协同落地”。

当前简历的主要问题：

- ApplyFlow 没有作为核心项目出现，导致 AI 岗最有竞争力的作品没有被面试官第一眼看到。
- 自我评价偏“管理类/销售运营/公文写作”，AI 产品与 Agent 系统能力不够突出。
- 工作经历顺序和项目经历表达容易让面试官觉得你是传统管理/运营候选人，而不是 AI Native Builder。
- 缺少作品集入口、内测证据、项目指标和工程化关键词。

结论：

> 不建议只在原简历里轻描淡写加一句 ApplyFlow。应该新增一个独立的“AI 产品项目 / 作品集项目”模块，把 ApplyFlow 放在网易 AI 实习之前或之后的高优位置。

## 3. ApplyFlow 项目应该怎么写

### 项目标题

ApplyFlow｜面向求职执行闭环的 AI Agent 工作台
个人作品 / Internal Beta 准备阶段 / 2026.04-2026.05

### 简历版描述

ApplyFlow 是一个面向求职场景的 AI Agent 作品集项目，重点不是“一键生成简历”，而是把岗位筛选、可解释排序、Shortlist/Compare、投递状态管理和反馈复盘串成可解释、可回归、可内测的执行闭环，用系统工程方式约束 AI 应用的不确定性。

### 完整项目经历（图片模板版，推荐放简历）

ApplyFlow - 面向求职场景的 AI Agent 执行工作台｜AI 产品 / AI 应用｜2026.04 - 2026.05

项目简介：参考 CareerOps 思路，基于 Agent Workflow + Human-in-the-loop 设计并实现求职执行系统，针对“岗位信息过载、机会判断不稳定、投递过程不可追踪”的业务痛点，构建从岗位导入、偏好建模、可解释排序、候选对比到投递状态追踪与反馈复盘的闭环流程；重点设计五维排序合同、状态机、系统边界与回归评测机制，提升求职决策效率、推荐可解释性与流程可控性。

技术栈：AI Agent Workflow、Structured Output、Tool Calling、Human-in-the-loop、State Machine、Eval Harness、Prompt Engineering、Playwright、Cloudflare Workers、SQLite / D1

技术亮点：

- 求职执行闭环：围绕“先筛后投”重构求职流程，将岗位导入、标准化去重、偏好建模、优先级排序、候选对比、投递状态与反馈复盘串联，避免停留在单点 LLM Demo。
- 可解释排序机制：设计 `userPriorityScore` 五维排序合同，从岗位方向、行业匹配、城市偏好、公司类型与投递可行性评估岗位价值，并统一 Grade、Verdict、雷达图、Compare 与 Gate 口径。
- 人机协同边界：明确 Agent 负责语义理解、匹配判断与解释建议；系统负责状态流转、权限校验、执行门禁与审计留痕；用户负责高风险决策确认与最终投递。
- 评测与回归验证：搭建轻量 Eval Harness，基于 5000+ 条真实岗位数据验证不同求职画像下的排序稳定性，并通过 Top100 分布、`highRoleFitButLowGrade`、关键写路径校验等指标发现回归问题。
- 投递流程优化：基于用户反馈重构“查看岗位→打开投递链接→加入投递清单→记录投递结果”的投递闭环；小样本走查中 5/5 用户完成投递记录闭环（完成率 100%），102 条岗位浏览转化为 17 条投递清单候选（16.7%），其中 10 条完成状态回填（58.8%），并将首屏干扰入口由 14 个收敛至 5 个。

### 面试官会沿着项目经历追问什么

- 场景到底是什么：不是“AI 求职工具”，而是“先筛后投”的求职执行场景。
- 为什么要用 Agent：因为求职是持续多步骤任务，需要理解岗位、偏好、状态和反馈。
- 为什么不用普通 workflow：workflow 能管状态，但不能充分处理 JD 和用户偏好的语义判断。
- 为什么不用传统规则：规则适合 gate、权限和状态，语义匹配和解释需要模型/启发式补充。
- 怎么证明不是玩具：真实池验证、投递漏斗、Bad Case 台账、回归脚本和用户反馈迭代。
- 如果问 SFT / Agentic RL：当前不硬包装，先积累用户操作轨迹、接受/拒绝理由、误排样本和解释可信度标签。

### 简历写法自检：不要浪费项目经历

不要只写：

- 搭建 AI Agent，配置 Prompt 和工具调用。
- 使用大模型实现岗位推荐。
- 优化 Prompt，提升回答效果。

要写清楚：

- 场景：求职者面对大量岗位，不知道先投哪个，投递后也缺少追踪。
- 设计：Agent 做语义判断，系统做状态、权限和执行门禁，用户做最终确认。
- 优化：根据用户反馈收敛投递主路径，从复杂面板改成投递链接、投递清单、状态回填和轻量反馈。
- 结果：用投递清单候选率、状态回填率、真实岗位池回归和 Bad Case 复测证明效果。
- 反思：当前不是成熟 SaaS，也不是全自动投递；下一步补线上埋点、真实用户试用和周期性评估报告。

详细准备见：

- `interview/ApplyFlow_Agent项目简历写法与面试落地表达.md`

暂不写入简历的内容：

- 不写“简历改写 / Resume Tailoring 已落地”，因为当前项目没有该功能。
- 不写“全自动投递 / 自动海投”。
- 不写“公开 SaaS / Production Ready / 大规模用户增长”。
- 优先写投递漏斗指标：投递记录闭环完成率、岗位浏览到投递清单转化率、投递清单到状态回填率；“首屏入口 14→5”只作为解释为什么投递流程更清晰的辅助证据。

## 5. 网易经历怎么改

当前网易经历建议统一改为：

> 网易｜AIGC 内容安全策略运营实习生

推荐写法：

- 参与 AIGC 内容生成场景的安全策略运营，协助梳理文本/图片生成中的风险类型、审核规则与用户反馈链路，支持策略从问题发现到迭代落地。
- 基于生成结果抽检与 Bad Case 复盘，整理模型输出不稳定、内容低质重复、敏感表达误判等问题，协助沉淀 Prompt 测试样例和策略优化建议。
- 对比人工创作内容与 AIGC 内容的审核差异，明确机器生成内容在规模化、不可控性、事实性和版权风险上的治理重点，形成可复用判定口径。
- 跟踪竞品 AIGC 功能与内容治理案例，输出体验分析和策略复盘，理解 AI 产品中模型能力、内容安全、人工复核与用户体验之间的平衡。

面试防守口径：

- 简历里用“参与、协助、沉淀、整理”，不要写“主导上线、负责核心模型、提升 XX%”。
- 如果被问具体指标，不要编准确率或转化率，可以说“我没有独立拥有线上指标，主要参与抽检标注、Bad Case 记录、风险归因和策略口径整理”。
- 如果被问 AIGC 和人工内容区别，要答“生成规模更大、输出更不稳定、风险更隐蔽，所以需要 Prompt 约束、策略规则、人工复核和复测机制”。
- 实习和 ApplyFlow 的连接是“AI 治理方法迁移”：网易实习看的是生成内容风险，ApplyFlow 看的是求职投递决策风险，本质都是让 AI 建议进入可观测、可复核、可迭代的系统边界。

## 8. README 是否适合直接给面试官

当前根目录 `README.md` 不建议直接发给面试官。

原因：

- 信息过长，像工程交接，不像作品集入口。
- 更新时间是 2026-04-29，和当前 demo / 3-5 人内测阶段不完全同步。
- 包含大量 phase 细节，面试官第一眼很难抓住价值。
- 有绝对本地路径链接，不适合外部阅读。
- 没有截图、作品集摘要、内测证据表。
- “当前阶段进入 partial_rebuild Phase 0”等内容会和后续进展产生混淆。

建议：

- 保留当前 README 给开发和交接使用。
- 新增一份面试官阅读版 one-pager。
- 如果之后要公开 GitHub，再把根 README 顶部改成作品集入口，把详细 phase 历史移到 docs。
