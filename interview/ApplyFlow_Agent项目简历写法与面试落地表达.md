# ApplyFlow Agent 项目简历写法与面试落地表达

最后更新：2026-05-19

## 0. 这组内容提炼成一句话

简历里写 Agent 项目，最忌讳写成“我搭了一个 Agent，配置了 Prompt 和工具调用”。这句话等于没写，因为面试官看不出你解决了什么问题、承担了什么核心工作、怎么优化、最后有什么效果。

更好的写法是：

> 我在什么业务场景里，遇到什么具体问题，为什么需要 Agent，怎么设计系统边界，踩过什么坑，怎么迭代优化，最后用什么指标证明效果。

对 ApplyFlow 来说，主线不是“我做了 AI 求职工具”，而是：

> 我围绕求职者“岗位太多、不知道先投哪个、投递后不可追踪”的问题，设计了一个先筛后投的 Agent Workflow，把岗位导入、偏好建模、可解释排序、投递清单、状态回填和反馈复盘串成闭环，并用评估脚本、投递漏斗和 Bad Case 复测证明它不是一次性 Demo。

## 1. 简历中不要这样写

不要写：

- 搭建 AI Agent，配置提示词和工具调用。
- 使用大模型实现岗位推荐。
- 基于 Agent 实现自动化求职流程。
- 优化 Prompt，提升回答效果。
- 接入 RAG/多模态/工具调用，完成智能分析。

这些问题在于：

- 看不出真实业务场景。
- 看不出你承担了哪部分核心工作。
- 看不出为什么必须用 Agent。
- 看不出如何评估效果。
- 看不出踩过什么坑和怎么解决。

面试官很容易追问两句就结束：你具体解决了什么？为什么这么设计？效果怎么证明？

## 2. ApplyFlow 应该怎么写

### 完整简历项目版本

```text
ApplyFlow - 面向求职执行闭环的 AI Agent 工作台｜AI 产品 / AI 应用｜2026.04 - 2026.05

项目简介：参考 CareerOps 思路，针对求职者“岗位信息过载、机会判断不稳定、投递过程不可追踪”的问题，设计并实现先筛后投的 AI Agent Workflow；系统覆盖岗位导入、偏好建模、五维可解释排序、候选岗位对比、投递清单、状态回填与反馈复盘，并通过评估脚本、真实岗位池和投递漏斗验证推荐稳定性与流程可用性。

技术栈：Agent Workflow、Structured Output、Tool Calling、Human-in-the-loop、State Machine、Eval Harness、Prompt Engineering、Playwright、Cloudflare Workers、SQLite / D1

技术亮点：
- 业务闭环设计：将求职流程从“手工海投”重构为“岗位发现→可解释排序→投递清单→状态回填→反馈复盘”，避免停留在单点 LLM Demo。
- 排序与解释机制：设计 `userPriorityScore` 五维排序合同，将岗位方向、行业匹配、城市偏好、公司类型和投递可行性统一到 Grade、Verdict、雷达图、Compare 与 Gate 口径中。
- 系统边界治理：明确 Agent 负责语义理解和解释建议，系统负责状态流转、权限校验、执行门禁和审计留痕，用户负责最终投递决策。
- 评估与回归机制：搭建轻量 Eval Harness，基于 5000+ 条真实岗位池验证不同求职画像下的 TopN 分布、排序异常和关键写路径边界，防止模型/规则调整造成回退。
- 用户反馈迭代：根据走查反馈收敛投递主路径，建立“岗位浏览→投递清单→状态回填”漏斗；小样本同口径复测中，投递清单候选率从 8.8% 提升至 16.7%，状态回填率从 33.3% 提升至 58.8%。
```

### 三条压缩版

```text
- 独立设计并落地 ApplyFlow AI 求职执行系统，围绕“先筛后投”重构求职流程，覆盖岗位导入、偏好建模、可解释排序、投递清单、状态回填与反馈复盘，避免停留在单点 LLM Demo。
- 设计 `userPriorityScore` 五维排序合同，将岗位方向、行业匹配、城市偏好、公司类型与投递可行性统一到 Grade、Verdict、Compare 和 Gate 口径，并基于 5000+ 条真实岗位池验证排序稳定性。
- 基于用户反馈优化投递主路径，建立“岗位浏览→投递清单→状态回填”漏斗；小样本同口径复测中，投递清单候选率 8.8%→16.7%，状态回填率 33.3%→58.8%，并沉淀 Bad Case 与回归脚本。
```

### 两条极简版

```text
- 独立构建 ApplyFlow AI 求职执行工作台，将岗位导入、偏好建模、可解释排序、投递清单、状态回填和反馈复盘串成端到端流程，解决求职中“岗位太多、先投哪个、投后怎么追踪”的执行问题。
- 搭建轻量 Eval Harness 与投递漏斗指标，基于 5000+ 条真实岗位池验证排序稳定性，并通过投递清单候选率 8.8%→16.7%、状态回填率 33.3%→58.8% 证明主路径迭代效果。
```

## 3. “我做了啥”改成“我怎么做好”

### 反例

> 搭建 AI Agent，配置 Prompt 和工具调用，实现岗位推荐。

### ApplyFlow 正确写法

> 我没有只配置 Prompt，而是把求职任务拆成岗位导入、标准化、偏好建模、排序解释、投递清单和状态回填，并明确 Agent、系统、用户三方边界。Agent 负责语义理解和解释建议，系统负责状态机、权限校验和执行门禁，用户负责最终投递确认。

面试官听到这里，会继续追问“怎么排序、怎么验证、怎么保证不串号”，这正好进入你熟悉的内容。

## 4. “优化提示词”改成“定位问题根因并闭环”

### 反例

> 优化 Prompt，提升推荐效果。

### ApplyFlow 正确写法

> 我在线上走查时发现用户打开投递链接后，页面里材料、高级记录、状态按钮混在一起，主路径不清楚。于是我不是简单改文案，而是重构投递主路径：优先展示打开投递链接、加入投递清单、标记已投递和反馈误判，将材料准备等未落地能力从主路径移除。改版后用同口径测试画像复测，投递清单候选率从 8.8% 到 16.7%，状态回填率从 33.3% 到 58.8%。

这里的面试重点是：

- 发现问题：用户反馈点击投递链接后内容混乱。
- 定位根因：不是推荐模型问题，而是执行路径和界面信息架构问题。
- 方案设计：减少干扰入口，收敛到投递清单和状态回填。
- 效果验证：用投递漏斗指标复测。

## 5. “做了评估机制”要写清楚评估了什么

不要只写：

> 搭建 Agent 效果评估体系。

ApplyFlow 应该写：

> 搭建轻量 Eval Harness，从任务结果、执行轨迹、系统边界和体验质量四层评估 Agent 效果：结果层看岗位是否进入投递清单、状态是否回填；轨迹层看排序、解释、反馈是否留痕；边界层看权限、数据归属和执行门禁是否被绕过；体验层看推荐理由是否可解释、用户是否采纳。

再补一句：

> 能用代码判断的指标用脚本做硬校验，比如 schema、状态、权限、TopN 异常和 forged userId；语义体验再用 LLM/人工抽检；真实用户价值用 Evidence Log 和 Bad Case 复测。

## 6. ApplyFlow 的“踩坑经历”怎么讲

### 坑 1：旧评估口径和真实用户价值不一致

回答：

> 我遇到过一个问题：如果评估只看历史标签命中率，系统可能为了过测试而推荐用户并不想投的岗位。后来我把排序评估迁移到 `userPriorityScore` 五维合同，用岗位方向、行业、城市、公司类型和投递可行性来统一生产排序和回归验证，避免评估目标和产品目标割裂。

### 坑 2：投递主路径被无关功能干扰

回答：

> 一开始岗位卡片里有很多执行管理入口，比如材料准备、高级记录、查看详情，但用户真实流程是点开岗位链接后去外部投递，再回来记录状态。所以我把主路径收敛为打开投递链接、加入投递清单、标记已投递和反馈误判。这个改动让投递清单候选率和状态回填率都有明显提升。

### 坑 3：隐藏筛选状态造成用户看不到岗位

回答：

> 我之前修过一个 localStorage 残留问题：用户切换过候选清单筛选后，隐藏状态会让旧用户看不到全部岗位。这个问题表面是 UI，实际是缓存状态和用户主路径冲突。修复后我用 Focused Review 检查状态错位、缓存残留和相邻回归，防止类似问题复发。

### 坑 4：投递链接不能用 demo 假链接

回答：

> 我发现打开投递链接时曾经出现 demo 域名，这对真实用户体验是致命的。后来我把岗位链接完整性单独作为验证项，区分 demo 展示链接和真实岗位 apply_url，避免用户以为进入了真实投递，实际却打不开。

## 7. 不同场景怎么加分

### 投 AI 产品经理

重点讲：

- 用户问题和流程闭环。
- 为什么先做岗位筛选而不是简历改写。
- 投递漏斗指标。
- 用户反馈如何驱动迭代。
- 人机协同边界。

一句话：

> 我不是为了做 Agent 而做 Agent，而是从求职执行问题倒推 AI 应该在哪些环节介入：语义判断交给 Agent，状态流转交给系统，高风险决策交给用户。

### 投 AI 应用 / Agent 岗

重点讲：

- Agent Workflow。
- Structured Output / Tool Calling。
- State Machine / Control Gate。
- Eval Harness。
- 安全边界和回归验证。

一句话：

> 我的项目重点不是调用一次模型，而是把模型放进可验证的工作流里，用 schema、状态机、权限、gate 和回归脚本把不稳定输出约束成可用系统。

### 投 AI 运营 / AIGC 内容安全相关岗位

重点讲：

- Bad Case 台账。
- 反馈复盘。
- 人工复核边界。
- Prompt 只是软约束。
- 评估和抽检。

一句话：

> 网易 AIGC 实习让我理解生成内容需要风险分级和人工复核，ApplyFlow 则是我把这套治理思路迁移到求职决策场景：AI 给建议，系统留痕，用户确认，Bad Case 进入复测。

## 8. 简历项目的万能检查表

写完每条项目经历后，逐条检查：

- 场景：面试官能不能一眼看出你解决的真实问题？
- 职责：能不能看出你做了核心设计，而不是只接 API？
- 方案：有没有讲为什么这么设计，而不是只列技术名词？
- 边界：有没有讲哪些交给 Agent，哪些交给系统，哪些交给用户？
- 评估：有没有指标、脚本、Bad Case 或用户反馈支撑？
- 结果：有没有前后对比或可验证产出？
- 反思：有没有讲踩过的坑和下一步？

## 9. 面试官问“你这个项目的核心亮点是什么”

可以这样答：

> 核心亮点不是我会调用大模型，而是我把一个模糊的求职问题做成了可执行、可评估、可复盘的系统。它有真实业务场景：岗位太多、机会判断难、投递后不可追踪；有系统设计：Agent 做语义判断，系统做状态和权限，用户做最终确认；有评估机制：真实岗位池、TopN 分布、投递漏斗、Bad Case 和回归脚本；也有迭代证据：根据用户反馈收敛投递主路径，并用投递清单候选率和状态回填率复测。

## 10. Focused Review 自审记录

Correctness Findings：

- 本文档将小红书内容转成 ApplyFlow 专属简历和面试表达，覆盖“不要只写做了什么，要写怎么落地、怎么优化、结果如何”。
- 简历 bullet 避免写未落地的简历改写、材料定制、全自动投递和大规模增长。
- 指标沿用既有小样本同口径走查口径：投递清单候选率 8.8%→16.7%，状态回填率 33.3%→58.8%。

Boundary/Safety Findings：

- 明确这些指标不是大规模线上指标，不包装成 DAU、留存或商业化数据。
- 明确 ApplyFlow 当前不是 RAG 项目，也不是全自动投递工具。
- 明确 Agent、系统、用户三方边界，避免把高风险动作说成自动完成。

Adversarial Scenarios Checked：

- 被问“你到底解决了什么问题”。
- 被问“是不是只配置 Prompt 和工具调用”。
- 被问“效果怎么证明”。
- 被问“踩过什么坑”。
- 被问“为什么不先做简历改写”。

Blast Radius & Adjacent Regression Assessment：

- 本轮只新增面试文档，不改运行代码、数据、部署配置或排序核心。
- 相邻文档需要同步主面试手册和简历材料方案。

Residual Risks：

- 若用户把本文档完整项目版本放进一页简历，可能偏长，需要根据版面压缩到 2-3 条。
- 面试前应确认 Evidence Log 中的指标截图、朋友试用原话和线上链接可访问。

Disposition：

- Unblocked。owner：项目作者。建议重点背第 2、4、6、9 节。
