# AI Agent 项目如何避免玩具感：简历与面试深挖清单

最后更新：2026-05-16

## 1. 核心判断

现在 AI Coding 与 Agent 工具发展很快，很多候选人都能用 Claude Code、Cursor 或开源模板快速搭出一个“能跑的 Demo”。因此，面试官不再只看你有没有做出一个 AI 项目，而是会判断：

- 这个项目是不是只停留在“玩具 Demo”。
- 项目场景是否真实，是否有明确用户和业务问题。
- 是否有取舍、评测、复盘和迭代证据。
- 是否能说明为什么要用 Agent，而不是普通 workflow 或传统规则。
- 是否有 Benchmark / Eval / Harness，而不是只靠主观感觉。

换句话说，简历项目要从“我做了一个功能”升级为“我围绕一个真实场景，设计了一套可评估、可迭代、可解释的系统”。

## 2. 简历项目的第一轮筛选

如果把项目描述或 README 直接丢给 Claude Code，它能不能快速做出一个差不多的项目？

如果可以，说明简历描述太像通用模板，缺少真正的项目壁垒。需要补充：

- 真实场景：用户是谁，任务是什么，为什么这个任务值得做。
- 业务卡点：不是“我用了 AI”，而是用户原来卡在哪里。
- 场景取舍：做了什么，不做什么，为什么。
- 评测证据：用什么指标证明改动有效。
- 迭代闭环：用户反馈、Bad Case、复测结果。

## 3. 面试官真正会问的不是“用了什么框架”

面试官通常不会最关心你用了 LangChain、LlamaIndex 还是 LangGraph。他们更关心：

- 你的场景到底是什么？
- 你解决了什么真实问题？
- 为什么这里需要 Agent？
- 为什么不用普通 workflow？
- 为什么不用传统规则？
- 实现过程中做过哪些取舍？
- 速度和准确性怎么权衡？
- 你怎么评估 Agent 效果？
- 你做过哪些 Harness / Benchmark 层面的优化？
- 你的系统表现和模型本身能力有什么关系？

技术栈可以写，但不能替代问题定义、系统设计和评估体系。

## 4. 玩具项目与可面试项目的区别

玩具项目常见特征：

- 只有理想路径 Demo。
- 简历描述和别人高度相似。
- 只堆 RAG、Agent、Tool Calling、Workflow 等名词。
- 没有真实用户反馈。
- 没有 Bad Case。
- 没有评测和复测。
- 不能解释为什么不用更简单的方法。

可面试项目应该具备：

- 有具体业务场景和用户任务。
- 有明确系统边界：AI 做什么，人做什么，系统 gate 什么。
- 有取舍：哪些功能主动不做，为什么。
- 有指标：任务完成率、耗时、错误率、转化漏斗、Bad Case 率等。
- 有评测：固定样本、回归脚本、Benchmark 或 Eval Harness。
- 有复盘：问题、归因、改动、复测、残余风险。

## 5. 必备追问清单

### Q1：你的场景到底是什么？

不能回答“我做了一个 Agent”。要回答“谁在什么任务里遇到什么问题”。

### Q2：你解决了什么问题？

要能说清楚用户原来怎么做、哪里低效、你的系统改变了什么。

### Q3：为什么要用 Agent？

回答重点不是“因为 Agent 很热门”，而是任务是否需要多步状态推进、工具调用、反馈记录和人机协作。

### Q4：为什么不用普通 workflow？

如果流程完全确定，普通 workflow 可能更合适。Agent 的必要性来自语义理解、模糊判断、动态解释和多来源输入处理。

### Q5：为什么不用传统规则？

规则适合确定性校验，LLM 适合半结构化文本理解和解释生成。好的系统通常是二者分工，而不是全交给模型。

### Q6：实现过程中做过哪些取舍？

例如速度 vs 准确性、自动化 vs 人工确认、功能完整度 vs 内测安全边界、模型能力 vs 系统可控性。

### Q7：怎么评估 Agent 效果？

需要有 Evaluation / Benchmark，而不是只说“看起来还不错”。

### Q8：你的 Harness 做了什么优化？

Harness 可以理解为固定输入、期望输出、运行脚本、指标和失败解释的评测脚手架。要能说出哪些 case、哪些指标、哪些失败会阻断。

### Q9：哪些表现来自模型，哪些来自系统？

优秀回答要区分模型能力和系统工程：模型负责语义理解，系统负责 schema、状态、权限、gate、日志、评测。

### Q10：如果要继续优化模型，你会怎么做？

可以提 SFT / Agentic RL，但不要硬装已经做了。更稳妥的回答是：先收集高质量轨迹、Bad Case、人工标注偏好和失败样本，再决定是否需要微调或强化学习。

## 6. 映射到 ApplyFlow

ApplyFlow 的核心场景：

> 求职者面对大量岗位时，不知道哪些值得优先投，投递后也难以追踪和复盘。

ApplyFlow 的非玩具点：

- 不是自动海投，而是“先筛后投”的求职执行系统。
- 有 5000+ 真实岗位池排序验证。
- 有 `userPriorityScore` 五维排序合同。
- 有 shortlist / compare / tracker / feedback 的状态闭环。
- 有投递流程优化指标：岗位浏览到投递清单、投递清单到状态回填。
- 有用户反馈、Bad Case、迭代记录和复测口径。
- 有系统边界：Agent 建议，系统 gate，用户确认。

## 7. ApplyFlow 面试回答模板

### 为什么要做这个项目？

> 我不是为了做一个 AI Demo，而是从自己的求职流程出发，发现真实问题不是“缺一段生成文案”，而是岗位太多、优先级难判断、投递后难追踪。所以我把 ApplyFlow 定位成 CareerOps 工作台，用 AI 先帮助用户判断机会价值，再用状态管理和反馈闭环把求职过程沉淀下来。

### 为什么要用 Agent？

> 因为求职不是单次问答，而是一个持续推进的多步骤任务。系统需要读取岗位、理解用户偏好、排序解释、加入投递清单、记录状态、接收反馈，并在高风险动作前让用户确认。Agent 负责语义理解和建议，workflow 负责状态和执行边界。

### 为什么不用纯 workflow？

> 纯 workflow 能管状态，但很难理解半结构化 JD 和用户偏好里的语义差异。比如“数据分析”“商业分析”“数据产品”“开发岗混合标题”之间不是简单关键词匹配。所以我用 LLM/启发式做语义判断和解释，再用确定性状态机和 gate 控制流程。

### 你做过什么取舍？

> 我主动放弃了默认全自动海投。因为外部投递涉及真实求职风险，错误提交的代价高。我的设计是：系统帮助用户判断和记录，投递动作由用户确认，状态和反馈进入系统复盘。

### 怎么证明不是玩具？

> 我不会只展示理想 Demo。ApplyFlow 有真实池排序验证、投递漏斗指标、Bad Case 台账和回归脚本。比如投递流程改版后，我记录了 5 个测试画像的投递记录闭环，102 条岗位浏览中有 17 条进入投递清单，10 条完成状态回填。这些不是增长数据，但能证明我在用真实任务逼出问题并迭代。

### 如果问 SFT / Agentic RL

> ApplyFlow 目前没有做 SFT 或 Agentic RL，我不会硬包装。我的优先级是先把高质量数据采集做好，包括用户接受/拒绝岗位的原因、误排 Bad Case、投递状态轨迹和解释是否可信。只有当这些轨迹积累到足够规模，才考虑用 SFT 学解释风格或用偏好数据优化排序策略。

## 8. 对简历的启发

简历里不要只写：

> 使用 Agent、Tool Calling、Eval Harness 完成求职系统。

更应该写：

> 基于求职投递场景构建“岗位浏览→投递清单→状态回填”漏斗，102 条岗位浏览产生 17 条投递清单候选，其中 10 条完成状态回填，并根据用户反馈将投递卡片从工程状态面板收敛为轻量投递清单。

这类描述更接近企业面试官关心的项目质量：场景、指标、取舍、复盘。
