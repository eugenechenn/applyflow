# AI Agent 系统治理与 Coding 难点面试准备

最后更新：2026-05-16

## 1. 从图片提取出的核心观点

LLM 输出本质上是概率采样，不是严格执行规则。Prompt 只能做软约束，不能把模型“锁死”。当用户输入模糊、噪声大、工具参数嵌套深、业务规则复杂时，只靠提示词很容易出现字段漂移、参数乱填、工具误调、输出格式不稳定等问题。

更稳的工程方案是三层防护：

1. Prompt 软约束：把规则写得更明确，例如不要只写“city 是城市名”，而要写“city 必须是标准英文城市名，如 Beijing，禁止传入自然语言短语”，并用 few-shot 示例给模型参考。
2. Schema 硬约束：用 JSON Schema / Structured Output / 枚举定义可机器验证的结构，声明必填字段、字段类型、枚举范围和 `additionalProperties: false`，防止模型随意加字段。
3. 校验-修复-重试闭环：模型输出后先做语法校验和 Schema 验证，失败时把错误信息回传给模型修复；重试必须有次数上限，超时或连续失败进入人工兜底。

架构层面的关键分离：

- 模型层：判断该调用哪个工具、生成候选参数、输出解释。
- 框架层：校验参数、控制工具权限、处理重试、记录状态。
- 工具层：实现真实业务动作，与模型解耦。

一句话总结：

> 顶级 Agent 不是 Prompt + Tools，而是 Prompt 编排、角色拆分、验证机制、工具治理和生命周期管理共同组成的系统工程。

## 2. 面试官真正想听什么

如果面试官问“你用 AI Coding 或 Agent 开发遇到过什么难点”，不要只说“模型有时会写错代码”。要回答成系统问题：

> 我最大的体感是，LLM 很适合生成候选方案，但不能把“生成”直接等同于“完成”。真正难的是把不稳定的模型输出放进一个可验证、可回滚、可人工接管的系统里。

可以展开成五层：

- Prompt 编排：静态规范 + 动态上下文，避免每轮上下文漂移。
- 角色拆分：探索、实现、验证分开，减少一个模型同时做所有事导致的自我确认。
- 验证机制：生成代码后必须跑 lint、typecheck、关键脚本、Playwright 或自审清单。
- 工具治理：高风险写入、部署、数据修改必须有权限边界和回退策略。
- 生命周期：长任务要记录当前目标、进度、下一步、风险点，避免中断后丢失上下文。

## 3. ApplyFlow 可以怎么映射

ApplyFlow 里可以讲的不是“我用了某个很酷的框架”，而是这些系统治理点：

- 模型边界：AI 负责岗位语义理解、推荐理由、风险摘要和候选建议；不能直接决定用户数据归属、真实投递提交或最终求职决策。
- Schema / 合同：`userPriorityScore`、Grade、Verdict、Gate、Feedback 都要有固定结构，避免 UI、排序和评测各说各话。
- 状态机：岗位从浏览、加入投递清单、已投递、面试中、拒绝、录用等状态推进，不能让模型自由改状态。
- 人工确认：外部投递链接、材料使用、最终提交都需要用户确认，AI 只做建议和辅助。
- 回归验证：排序合同、真实池 Top100、demo 池、多用户隔离、伪造 `userId` 拒绝，都要变成脚本或自审清单。
- 文档化生命周期：`AGENTS.md`、`CONTEXT.md`、`TIMELINE.md` 用来约束任务流程、记录当前现场和变更历史，避免长任务中断后失控。

面试可说：

> 我在 ApplyFlow 里学到的核心不是“怎么让模型回答得更像”，而是怎么把模型的输出接进确定性系统。比如推荐理由可以由模型生成，但排序口径、状态推进、用户归属、投递门禁和回归验证必须由系统兜住。

## 4. Coding 难点故事库

### 4.1 难点一：AI 输出和产品状态不一致

问题：

> 推荐结果看起来合理，但如果状态管理混乱，用户不知道下一步该做什么，甚至点开投递链接后还要回到复杂面板记录一堆无关内容。

处理：

- 先从用户视角梳理主路径：查看岗位、打开投递链接、加入投递清单、记录投递结果。
- 删除或隐藏首屏干扰项，把材料准备、高级记录等未完成能力降级。
- 将“点击投递链接后是否加入投递清单”设计成清晰提示，而不是让用户回到复杂详情页。

面试表达：

> 这个问题本质不是 UI 小修，而是执行流和状态机不一致。用户真正任务是投递，不是填写一堆系统字段，所以我把主路径收敛成投递清单和状态回填。

### 4.2 难点二：局部缓存导致状态错位

问题：

> 某次优化后，旧用户因为本地 `localStorage` 里残留了投递清单筛选状态，进入页面时看不到全部岗位，表现像数据丢了。

处理：

- 先复现旧用户路径，确认不是后端数据问题。
- 定位为前端筛选状态与新流程默认态不一致。
- 修复默认筛选逻辑，让旧缓存不会误导用户进入错误视图。

面试表达：

> 这让我意识到 Agent 产品的稳定性不只是模型输出，还有状态一致性。前端缓存、后端真实数据、用户当前视图必须有清晰 source of truth，否则用户会觉得系统不可信。

### 4.3 难点三：不能只靠 Prompt 防止工具乱调

问题：

> 如果让模型直接决定工具参数，很容易出现字段缺失、枚举错误、额外字段、把自然语言塞进结构化参数等情况。

处理：

- Prompt 写清楚字段含义和禁止项。
- 结构化输出约束字段、类型、枚举和额外字段。
- 后端再做校验、失败重试和人工兜底。

面试表达：

> 我不会把 Prompt 当成安全边界。Prompt 是软约束，Schema 和后端校验才是硬边界。高风险动作必须经过系统 gate，而不是相信模型“应该会听话”。

### 4.4 难点四：评测目标和产品目标不一致

问题：

> 如果旧评测还在看历史标签命中率，但产品实际目标已经变成“用户价值排序”，就会出现测试通过却用户体验变差的情况。

处理：

- 把评测合同迁移到 `userPriorityScore`，让排序、UI 展示、Gate 和回归脚本同源。
- 用真实池 Top100 和 `highRoleFitButLowGrade` 检查明显误排。
- 对 demo 池和 real pool 分开验证，避免为了演示改坏主排序。

面试表达：

> AI 应用里的 eval 不是越多越好，而是要和产品目标对齐。否则 harness 会把系统往错误方向优化。

### 4.5 难点五：长上下文开发容易遗忘边界

问题：

> 用 Codex / Claude Code 这类工具长时间开发时，模型可能忘记之前的设计决定、误改不相关文件，或把临时方案当成最终方案。

处理：

- 用 `AGENTS.md` 固化项目规则。
- 用 `CONTEXT.md` 只保留当前目标、进度、下一步和注意事项。
- 用 `TIMELINE.md` 记录阶段性变更。
- 每次阶段性修改后做 Focused Review，检查正确性、安全边界、状态错位、缓存失效和相邻回归。

面试表达：

> AI Coding 的关键不是让模型多写代码，而是给它工程护栏：上下文压缩、任务边界、验证命令、禁止误改范围和审查清单。否则速度越快，风险也越快。

## 5. 你的 AGENTS.md 就是系统工程证据

这部分可以成为你面试里很有差异化的点。很多人只会说“我用 AI 写代码”，但你可以说：

> 我不是把 Codex 当成一次性代码生成器，而是把它放进一套工程流程里使用。我的 `AGENTS.md` 相当于项目级系统提示词和开发治理规范，规定文件编码、文档读取顺序、验证分层、禁止误改范围、Focused Review 和安全边界检查。它本质上就是我给 AI Coding Agent 设计的运行协议。

### 5.1 `AGENTS.md` 体现了什么能力

可以拆成五类系统工程能力：

- 上下文治理：先读 `CONTEXT.md`，再按需读 `DECISIONS.md`、`TIMELINE.md`、`VALIDATION_SPEED_POLICY.md`、`README.md`、`ARCHITECTURE.md`，避免模型每次从零理解项目。
- 变更边界：明确不能随意改排序核心、数据库、部署配置、无关文件；遇到用户已有改动不能回滚，体现 source-of-truth 和最小变更原则。
- 验证分层：不是每次都全量测试，而是按 L1/L2/L3 和风险范围选择验证，兼顾速度和质量。
- 安全门禁：涉及数据删除、DB 写入、生产部署、用户归属、缓存状态和共享层改动时必须先确认或做扩大 review。
- 复盘留痕：`CONTEXT.md` 记录当前现场，`TIMELINE.md` 记录阶段变更，`Focused Review` 记录正确性、安全边界、对抗场景和残余风险。

面试可说：

> 我把 AI Coding 流程设计成“任务协议 + 上下文管理 + 变更门禁 + 验证回归 + 复盘留痕”。这和 Agent 产品设计其实是一回事：模型负责生成候选动作，系统负责边界和验证。

### 5.2 你的开发流程怎么讲

可以按这个顺序讲：

1. 明确目标：先把用户需求转成当前目标和不可改边界。
2. 读现场：读取 `CONTEXT.md` 和相关设计文档，确认项目当前状态。
3. 定影响面：判断是文档、前端、排序、Auth、数据库还是部署问题。
4. 小步修改：优先局部变更，不扩大到无关模块。
5. 分层验证：根据风险跑对应脚本、页面 smoke、Playwright 或人工检查。
6. Focused Review：检查正确性、安全边界、状态错位、缓存失效、共享层扩散和相邻回归。
7. 更新现场：把新的状态写回 `CONTEXT.md` / `TIMELINE.md`，方便下次继续。

30 秒回答：

> 我的开发流程不是让 AI 一次性生成完代码，而是先读当前现场和设计文档，确认影响面和不可改边界，再小步修改、跑分层验证，最后做 Focused Review。比如之前投递流程改版后，我不仅检查 UI 是否能用，还专门查了旧用户缓存状态、投递清单筛选、用户归属和相邻路径，最后把结论写进文档。这就是我理解的 AI Coding 系统工程。

### 5.3 面试官追问：这不就是写文档吗？

回答：

> 不是普通文档。普通文档是给人看的说明，而我的 `AGENTS.md` 更像 Agent 的操作协议：它约束模型先读什么、不能改什么、遇到高风险怎么处理、验证至少覆盖哪些对抗场景。对 AI Coding 来说，缺少这类协议，就很容易出现上下文遗忘、误改、过度重构和自我确认。

### 5.4 面试官追问：为什么这能体现系统工程？

回答：

> 因为系统工程的核心不是写更多代码，而是让复杂系统在变化中仍然可控。我这里做了四件事：第一，定义输入上下文；第二，限制动作边界；第三，建立验证和回归；第四，记录状态和残余风险。这个思路和 ApplyFlow 产品里的 Agent 边界是一致的：AI 可以建议，但不能绕过系统门禁。

### 5.5 面试官追问：你怎么防止 AI 误改？

回答：

> 我主要靠三层：第一是文档层，`AGENTS.md` 写清楚禁止回滚用户改动、禁止扩大范围、禁止生产部署；第二是流程层，每次先确认影响面，避免共享层误伤；第三是验证层，修改后必须检查正确性、安全边界和对抗场景。对高风险路径，比如用户数据归属、投递状态、缓存和排序合同，不能只看 diff，要看相邻流程。

### 5.6 可以主动展示的材料

如果作品集里要放工程化证据，可以放一小块“AI Coding 工作流治理”：

```text
需求确认
→ 读取 CONTEXT / DECISIONS / TIMELINE
→ 判断影响面与不可改边界
→ 小步实现
→ 分层验证
→ Focused Review
→ 更新 CONTEXT / TIMELINE
```

配一句：

> 我把 AI Coding 从“生成代码”约束成“可审查的工程流程”，用项目协议、验证分层和 review 清单降低模型误改与上下文漂移风险。

## 6. 高频追问与回答

### Q1：LLM 工具调用参数乱传怎么办？

> 我会做三层约束：Prompt 写清字段含义和反例，Schema 定义字段、类型、枚举和禁止额外字段，执行前再做服务端校验。失败时进入修复-重试，但重试有上限，仍失败就转人工或降级，不让错误参数进入真实工具。

### Q2：为什么说生成不等于完成？

> 因为模型生成的是候选结果，不代表结果已经满足业务约束。完成必须经过校验、权限、状态落库、用户确认和可观测记录。ApplyFlow 里岗位推荐可以生成，但加入投递清单、状态回填、外部投递都要经过系统和用户确认。

### Q3：如果模型升级，你怎么保证不回退？

> 我会先跑固定样本回归，包括排序 TopN、Schema 合法率、错误枚举、Bad Case 集合和关键用户流程。模型升级不能只看个别回答更自然，而要看是否破坏排序合同、成本、延迟和安全边界。

### Q4：你怎么做 Bad Case 归因？

> 我会先分层定位：输入数据质量、模型语义理解、排序合同、工具参数、状态机、前端展示和权限边界。不要一看到坏结果就改 Prompt，很多问题其实是数据源、状态或评测口径不一致。

### Q5：你怎么理解 Human-in-the-loop？

> 不是页面上放一个“确认”按钮就叫人机协同，而是要定义哪些动作必须暂停、用户能 approve / edit / reject 什么、状态如何恢复、拒绝原因如何记录。ApplyFlow 里真实投递和高风险决策由用户确认，AI 只负责建议和解释。

## 7. 面试控场：把问题引回你熟悉的内容

当面试官问很散的问题时，用这四个锚点拉回 ApplyFlow：

1. 真实场景：求职不是单次问答，而是“岗位浏览到投递状态回填”的连续任务。
2. 系统边界：模型做语义判断，系统做状态、权限、Schema、Gate，用户做高风险确认。
3. 评测证据：真实池、demo 池、投递漏斗、Bad Case 和回归脚本。
4. 工程治理：Prompt 只是软约束，Schema、校验、重试、日志和 Focused Review 才能把黑盒变稳定。

万能转场句：

> 这个问题我会先拆成模型能力和系统工程两层。模型能不能生成只是第一步，真正决定能否上线的是 Schema、状态机、权限、评测和人工兜底。ApplyFlow 里我也是按这个思路做的。

## 8. 面试中不要这么说

- 不说“我看过某某泄露源码，所以照着做”，可以说“我关注到行业里对顶级 Agent 系统的公开讨论，核心共识是 Agent 竞争正在从模型能力转向系统工程”。
- 不说“Prompt 写好就稳定了”，要说 Prompt 只是软约束。
- 不说“我做了完整自动投递”，要说外部投递是辅助和人工确认。
- 不说“已经 production ready”，要说当前是 demo 到小规模白名单内测阶段。
- 不说“我主导了所有 RAG / SFT / RL”，ApplyFlow 当前没有这些能力，只能讲理解和下一步数据建设。

## 9. 可背版总结

> 我理解的 Agent 工程不是 Prompt 加工具，而是把概率模型放进一个可验证、可恢复、可人工接管的系统。模型负责理解和生成候选结果；系统负责 Schema、状态机、权限、工具治理和评测回归；用户负责高风险确认。ApplyFlow 的核心价值就在这里：我没有做一键海投，而是把岗位筛选、投递清单、状态回填和反馈复盘做成可追踪流程，用工程边界把 AI 的不确定性控制在可接受范围内。

补充一版“开发流程”总结：

> 我自己的开发过程也是按这个逻辑做的：用 `AGENTS.md` 给 AI Coding Agent 定义操作协议，用 `CONTEXT.md` 保持任务现场，用 `TIMELINE.md` 留痕变更，用 Focused Review 检查正确性、安全边界、缓存状态和相邻回归。也就是说，我不是只会调用 AI，而是在练习怎么治理 AI。
