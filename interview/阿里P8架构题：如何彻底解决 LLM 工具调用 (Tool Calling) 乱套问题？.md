## 🧠内容总结

这组笔记深度拆解了 LLM 在工具调用（Tool Calling）时常常“胡编乱造参数”的系统性顽疾。作者犀利指出，单纯迷信“优化提示词”是极其幼稚的，控制模型调用工具本质上是一个**软件工程问题**。优秀的 Agent 系统必须通过“提示词软约束 $\rightarrow$ Few-shot 锚定 $\rightarrow$ JSON Schema 硬约束 $\rightarrow$ 校验重试闭环”构建四层防御体系，并在架构上实现模型决策与执行骨架的彻底解耦，把可靠性责任从不可控的模型肩膀上卸下来。

## 📌关键信息

- **幻觉是系统特征**：模型在复杂参数下出错并“自信地瞎编假参数”，是当前大模型范式的系统性特征（概率性），单靠“好好说话（软提示）”根本拦不住。

- **提示词的准确定位**：Prompt 优化有价值，但它只是约束体系的第一层，且必须写得像“操作合同”（列明边界与非法值），而不是简单的自然语言描述。

- **硬约束的降维打击**：必须引入机器可读的结构化约束（JSON Schema）。用 `type`, `enum`, `required`, `additionalProperties: false` 等字段强制设立栏杆，从生成源头/解码阶段规避格式违规。

- **防死循环的兜底底线**：重试机制（Retry）必须设置明确的上限阈值。超过阈值必须果断降级或转人工，否则死循环重试会引发更大的系统灾难。


## 🧩方法/模型（可复用）

**1. Tool Calling 可靠性四层防御模型（从软到硬）**

在为 Agent 接入任何外部 API 时，必须打穿这四层：

- **L1 软约束（操作合同）**：在 System Prompt 中精确定义参数类型、边界和禁止传入的非法值。

- **L2 行为锚定（Few-shot）**：在上下文中直接给入“正确的用户输入 $\rightarrow$ 正确的工具调用”对照组，利用上下文学习锁定行为模式。

- **L3 硬约束（JSON Schema）**：在 API 层面对接 JSON Schema，强制模型输出机器可验证的结构化 JSON，拒绝多余幻觉字段。

- **L4 生产级闭环（校验-修复-重试）**：

    拿到模型输出 $\rightarrow$ `语法校验` $\rightarrow$ `Schema验证` $\rightarrow$ `自动清洗`（正则去除Markdown标记等） $\rightarrow$ 失败则将错误信息打包喂给模型发起 `重试请求`（标明错在哪）。


**2. 稳态 Agent 的三层分离架构（极具面试杀伤力）**

摒弃让 LLM 包揽一切的思维，在架构图上明确划清界限：

- **模型层（决策大脑）**：只负责接收意图、判断调哪个工具、生成参数。（输出是_概率性_的）

- **框架层（执行骨架）**：负责接收决策、执行 Schema 校验、调用实际 API、处理重试逻辑、整合结果。（执行是_确定性_的，负责兜底防线）

- **工具层（业务能力）**：具体功能实现。与模型完全解耦，工具逻辑变更无需重写 Prompt，只需改 Schema 契约。


## 🎯适用场景

- **高阶 AI 面试对答**：当被问到“如何保证 Agent 的稳定性”或“工具调用频繁失败怎么办”时，抛出“四层防御体系”和“三层分离架构”，直接展现资深工程视野。

- **复杂业务 Agent 落地**：在设计诸如“研报数据精准提取”、“自动投递简历”等不允许出错的 Agent 工作流时，作为核心的防错开发规范。例如在 Coze/Dify 中编排节点时，不要将 API 直连大模型，中间必须强插一个“代码执行/校验节点”作为框架层的过滤。

- **探索下一代前沿**：解决参数“格式”后，下一步的护城河在“参数语义”验证（如利用知识图谱将“沪”和“上海”对齐映射），可作为项目未来的迭代亮点。
